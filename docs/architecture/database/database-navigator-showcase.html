01

为什么它不是一个「连接列表」

四处「看着有、其实是假」的底座，逐条换成了真东西
旧样子（V1）现在
平铺一张连接表：没有分组、没有标签，库一多只能靠名字硬扫 分组 = 结构（可排序、多对多、主组全亮）+ 标签 = 检索（多值、不进树）+ 归属域 facet + 搜索语法 type: / scope: / tag: / driver:
「来源 / 作用域」被做成标签页分区，与行内标记重复表达同一件事 归属域回归事实属性：行内右对齐固定列（可关）+ 筛选；一级结构位让给用户自己的分组
展开对象树现查现拉，卡住界面；挂了只看到一句 CONN_NOT_FOUND 展开即建连；加载走后台线程 + 结果队列；失败带可读原因与重试入口，不静默吞错
刷新即清、断开即删缓存文件：「看起来更快」，代价是每次重扫 缓存只增不删：刷新只重建该范围；唯一删除入口是显式「缓存管理…」——这是从 v1 教训换来的规则
02

三条轴各归一地问

裁决「信息放哪」的三条边界规则

一问一主：三个问题各有且仅有一个承载位；任何信息不许同时占两位。

你问谁回答表达位禁止
我的库放在哪分组（结构容器，多对多）树一级（唯一结构轴）不做自动分类
和什么相关的库标签（横切检索键，多值）筛选 + 搜索；行内可选显示不进树、不排序
这一条记录存在哪归属域（P / G / GP）行内右对齐固定列 + 筛选不参与组织
这是什么库 / 能不能用类型（形状）+ 状态（颜色）同一个徽标的两个通道不靠颜色表达类型、不常显全名
这一个的细节属性面板（事实唯一权威位）编辑区右侧停靠面板导航行不重复这些细节
心智模型：导航栏的职责 = 定位 + 连接 + 浏览；配置归对话框，详情归属性面板。 结构靠分组，检索靠筛选，细节靠面板。事实只读，组织可写。
03

三个高光

如果只记三件事
HIGHLIGHT 1

一行只说三件事，且一个元素能说两件

常驻只有「徽标 + 名称 + 归属域列」，且归属域右对齐成列，长名不会挤走它。 徽标本身是双通道：颜色 = 状态（灰 = 不可用 / 彩 = 可用），形状 + 内叠 2 字母 = 数据库类型。 行尾 +（加标签）与 ✎（编辑）只在 hover / 选中时出现。

密度预算 ≤ 3长名截断不挤压连接 / 断开只走右键hover 卡 300ms 补全事实
HIGHLIGHT 2

事实只读，组织可写

类型、驱动、归属域、地址、状态是系统事实，只做展示与筛选；分组与标签是用户心智，才是可写组织。 所以信息永不「同时占两位」：在哪 = 分组，符合什么条件 = 筛选，这一个的细节 = 属性面板。

分组多对多 · 主组全亮其余组以引用行出现，点击跳回标签永不进树
看三条边界规则 ↑
HIGHLIGHT 3

展开不卡，错了有原因

树加载、属性、预热、预取全部进单一后台工作线程 + 结果队列；渲染期不做 I/O。 大 schema 靠类别文件夹分页顶住，首次展开表文件夹后还会顺手预取前 20 张表的列。 连不上就说清差在哪，并给重试入口。

首批 200 条 + 加载更多预热可取消 · 有进度节点级失败可读原因 + 重试

一次展开的全流程

从点到一根枝，每一步都有明确归属
STEP 1
面板就绪
归属域 chips + 筛选 + 搜索常驻；分组与标签这类本地小读走 defer_in 回填。
NavView
STEP 2
展开连接根
未建连先自动建连；建连失败只给可读原因与重试，不排加载。
NavHost ▸ 连接服务
STEP 3
请求下一级
只提交路径（连接 / 库 / schema / 表…），不阻塞 UI。
nav_jobs 入队
STEP 4
L1 内存
本会话取过的节点直接命中。
NavigatorService
STEP 5
L2 每连接 SQLite
跨重启的元数据缓存；命中即渲染，不必碰数据库。
cache-aside 回写
STEP 6
L3 实时内省
驱动按能力位内省（有没有独立 Schema 层由驱动声明）；结果回写 L2。
MetadataService ▸ MetadataBrowser
STEP 7
回填渲染
后台线程产出结果，主线程轮询取回；类别文件夹首批 200 条 + 「加载更多」。
结果队列
STEP 8
顺手备好下一层
表文件夹首次展开后，后台预取前 20 张表的列；连接成功后可提交预热（可取消、有进度）。
预取 / 预热
三条纪律：① render 期零 I/O（加载一律入队 + 回填）；② 缓存只增不删（清理只经显式「缓存管理」）； ③ 层级的数据库差异只在服务层与驱动能力位，节点模型与渲染层不为类型分叉。

cache-aside：命中即渲染，未命中才内省

L2
每连接 SQLite

可迁移 · 带版本
L3
实时内省
驱动 MetadataBrowser 直连目标库；它不是缓存，结果按 cache-aside 回写 L2。
驱动能力位
LAYER
层级随类型
有没有独立 Schema 层由驱动声明：MySQL / SQLite / DuckDB 无（Catalog 直接挂类别），PostgreSQL 有。

08

刷新 · 预热 · 预取

让「常用路径」先备好，同时一个字节都不删

⟳刷新粒度

  • ⟳：刷新当前选中连接
  • ⋯ → 刷新全部元数据：清掉已加载子节点后重载仍展开的连接根
  • 节点右键 → 刷新元数据：只重建该范围
  • 保留展开态，重新渲染时按需再懒加载

≋预热（连接成功后）

  • 提交后台内省 catalogs / schemas 写入 L2
  • 进度可见：面板头显示「预热 n/m」，可取消
  • 不阻塞 UI：进度是原子量，主线程轮询重绘

▤邻接预取

  • 表 / 视图文件夹首次展开后，后台预取前 20 张表的列
  • 失败静默——预取是加成，不是前置条件
  • 大 schema 另有 200 条分页 + 「加载更多」兜底
缓存只增不删：唯一删除入口是 ⋯ → 缓存管理…

架构 · 视图自带，能力靠端口

依赖只向下，面板不反向依赖工作台
数据链路
浏览一个对象：NavView → nav_jobs（工作线程）→ NavigatorService → MetadataService → 驱动 MetadataBrowser → 目标库
组织数据
NavView → nav_store → ConnectionOrgStore → project.db / global.db； 分组（含 is_primary）与标签是独立表，按存储域分区
视图状态
展开 / 选中 / 过滤存 navigator_state：项目 / 共享连接落 project.db，全局连接落 global.db； 跨重启保留，运行时连接不保留
徽标来源
engine::persistence::driver_catalog 读 drivers 表 → 类型形状与驱动显示名（一次性加载，渲染期零 I/O）
无中间层
进程内直连驱动，无 HTTP / 无 IPC；元数据走两级缓存，组织数据走 SQLite

依赖方向（硬约束）

app ▸ Feature crates ▸ engine ▸ shared ·Feature ▸ gpui-kit ·Feature ▸ workbench_shell ·任何 crate ▸ paths

本模块：视图在 crates/database 内自带

nav_view.rs
NavView 实体：面板头 / 分组树 / 连接行 / 对象树 / 右键 / 拖拽 / 行内编辑
nav_host.rs
NavHost 端口（宿主实现）:连接清单与选中 · 项目根 · 提示与重绘 · 视图偏好 · 连接生命周期 · 需要窗口的对话框
nav_store.rs
标签 / 分组 / 排序 / 导航状态落库——只依 engine + 项目根，不进端口
nav_jobs.rs
后台任务：加载 / 预热 / 预取 / 生成 SQL / 测试连接（单一工作线程 + 结果队列 + 原子进度）
其余
navigator_service 层级与懒加载编排 · metadata_service 内省调用 · model / cache 节点模型与 L2 读写 · property_panel 属性投影 · commands 键盘动作
为什么单独说这件事：面板视图以前住在工作台里，要穿过共享状态与一堆工作台服务。 视图下沉后，它只认一个自己定义的 trait（NavHost）：落库、驱动目录、对象树元数据这些「只依引擎」的能力不进端口，直接调。 于是依赖单向、面板可独立演进与测试，工作台侧只剩「持有实体 + 转发渲染」。
