# 元数据缓存：与 DBeaver / DataGrip 的深度对比

> **写作背景**：本仓的元数据缓存是**对标 DBeaver / DataGrip 的大库多 schema 浏览**设计的
> （依据：`engine/src/persistence/metadata_cache.rs:10`「大型数据库（如 Oracle）可能有 10 万+ 张表」、
> `engine/src/driver/introspection.rs:7`「内省级别对标 DataGrip 2026.1」、
> `database-nav-dev-plan.md:307`「大 schema（10 万+ 表）渲染卡顿 → `get_tables_chunk` 分页 + 虚拟列表」）。
> 本文把这条设计意图与两款成熟产品逐维度对照，用于判断「还差什么」与「哪些不该学」。
>
> 基线：2026-09-19（含 9-17 的 L1 回填与连接池、9-18 的导航侧分页消费、9-19 的**内容档全文搜索**与结构对象引用收敛）。
>
> ⚠️ **关于对标对象的说明**：DBeaver / DataGrip 的描述取自两者**公开的产品行为与文档**，
> 未按具体版本逐条核验内部实现（两者都不开源到可直接引用的程度，DataGrip 为闭源商业产品）。
> 因此下文对两者只用「公开行为」表述，不下断言式实现细节；**凡涉及本仓的结论均为代码实测**（标 ［验］）。

---

## 1. 两款产品在这件事上的取向（一句话）

| | 取向 | 直接后果 |
|---|---|---|
| **DBeaver** | **会话内内存缓存**：元数据随连接会话存在，断开/重启即丢，重连重新内省 | 实现简单、无一致性债；代价是**重连必重拉**，大库体验取决于网速与内省速度 |
| **DataGrip** | **持久化缓存 + 内省级别**：内省结果落在 IDE 的本地缓存里，断连也能看结构、能补全、能全库搜索 | 大库体验最好（搜索/补全不吃网络）；代价是缓存一致性、生命周期、以及"缓存过期了怎么办"的全套治理 |
| **本仓** | **第三条路：持久化到每连接一个 SQLite 文件 + 可管理** | 兼顾"重连秒开"与"离线可浏览"，且缓存是**用户可见、可删的资产**（有「缓存管理」对话框）；代价是要自己承担格式版本、失效与清理（见 §4） |

> 本仓这一选择不是拍脑袋：它是**本地优先**产品（服务对象是"查询结果落到本地 DuckDB 再分析"），
> 元数据缓存除了导航，还被 mock 导入列结构复用（`workbench/src/services/mock_generator.rs:452-491`），
> 所以"落盘、可复用、可清理"是产品需求，而不是纯性能优化。

## 1.5 优劣势速览（先说结论）

| | 优势 | 劣势 |
|---|---|---|
| **DBeaver** | 零持久化成本（不落盘 ⇒ 无一致性/版本/清理问题）；JDBC 生态驱动覆盖广；用户心智最简单——“刷新就是刷新” | 重连必重拉（大库/慢网首次展开慢）；断连不可浏览；搜索通常要回库或只搜已加载节点；拉取本身仍是一次性（客户端过滤省的是显示不是取数） |
| **DataGrip** | **本地持久模型**：断连可浏览、可补全、可全库搜索；**内省级别**（Auto/1/2/3）按对象数自动降级；同步粒度可配（整源 / 选中 schema / 对象）；多窗口共享同一份模型缓存 | 一致性治理成本高（“什么时候过期”需同步语义 + 状态显示）；缓存对用户**不可见不可管**（看不了“占多大、哪个库的、能否删”）；重量级 IDE 平台、闭源 |
| **本仓** | **落盘 + 可管理**：每连接一个 SQLite，可看大小、可删；同一份缓存服务导航 / 属性面板 / mock 导入列结构 / 生成 SQL 的列模板（不只服务树）；缓存与搜索的**写时机、分档、结果键都有测试锚住**（L1 命中用“空连接管理器”反证、池接线用“占住池连接”反证、分页/搜索用“空连接管理器下仍能命中”反证、分页键与搜索行键同构有单测） | **大库可翻、可搜，但仍不能“定位”**：大 schema（> 500 对象）按索引分页 + 「加载更多」；名称档（中缀）与内容档（注释 / 数据类型，trigram）两档已接，但**源码（定义文本）不入索引**；分块行不含注释；搜索结果**不能在树中展开并高亮**；自建成本高（格式版本 / 失效 / 清理 / 多实例都要自己扛） |

**取舍结论（本仓向谁学什么）**
- 学 DataGrip：**内省级别**（已接）与 **搜索走缓存**（已接：名称档 + 内容档，见 §4.6）；
- 学 DBeaver：**刷新语义要简单可解释**（右键刷新 = 清 L1 + 重写该 schema 的 L2）——比“会话内不落盘”更好解释，也比 DataGrip 的增量同步更便宜；
- 不学 DataGrip 的“本地模型 ↔ 库结构 diff”：本仓只存“上次从驱动读到的事实”，过期判断只靠 `fresh` 与 TTL，不做结构 diff（diff 属增量同步，见 §5）。

## 2. 逐维度对比

| # | 维度 | DBeaver | DataGrip | RdataStation（本仓，［验］） |
|---|---|---|---|---|
| 1 | 元数据来源 | JDBC `DatabaseMetaData` + 各驱动 MetaModel 补方言 | 各 dialect 的 introspector（平台内建对象模型） | 自建驱动层：`Database` trait + `MetadataBrowser`（6 个实现）；`MetadataService` 为唯一闸门 |
| 2 | 缓存层级 | 会话内内存（单层） | 内存模型 + 本地持久缓存 | **L1 内存**（进程内）→ **L2 每连接 SQLite** → **L3 实时内省**（文档明写「L3 不是缓存」） |
| 3 | 缓存标识 | 连接会话 | 数据源 id（+ 库/schema 维度） | `conn_{id}.sqlite`；**规划中**换「身份指纹」`meta_{fp}.sqlite`（同一物理库多连接共享，`metadata_identity` 已写但未接线） |
| 4 | 刷新粒度 | 节点级 F5（含强制刷新）；对象级 | 数据源级 Synchronize（可只同步选中的 schema/对象）；可设自动同步 | 节点级（右键「刷新元数据」→ `fresh=true`）→ 清 L1 + 重写该 schema 的 L2；**断连保留 L2** |
| 5 | 大库（10 万表）策略 | 懒加载 + 客户端过滤（配置过滤规则隐藏系统对象等）；**拉取本身仍是一次性** | **内省级别**（Auto/1/2/3，按对象数自动降级）+ 分库分 schema 懒加载 + 大库同步警告 | ［验］**分页已全线接通**（2026-09-18）：> `CHUNK_THRESHOLD`（500）的 schema 展开时只从 `metadata_index` 取一页（`get_objects_chunk`，表/视图各自分块）+「加载更多」按 `offset` 追加；≤ 500 仍走 L1 全量（零回归）；内省级别用于门禁预取 |
| 6 | 元数据搜索 | 对象搜索（基于已加载/可按需查询） | **Search Everywhere**（走本地持久缓存，不查库）——这是 DataGrip 的核心体验优势 | ［验］**两档已接**：名称档（`metadata_index`，中缀 LIKE，导航面板 + Quick Open 默认档，≥ 2 字）与内容档（`metadata_fts`，trigram，注释 / 数据类型，Quick Open `#` 档，≥ 3 字）；跨连接、后台、无缓存的连接不建文件，结果行键统一走 `ObjectRef::key()`。**未做**：源码（定义文本）搜索、“在树中定位” |
| 7 | 断连/离线 | 断开后缓存丢失，树需要重连 | 缓存保留 → **断连可看结构、可补全** | ［验］**L2 保留**（设计明确「断开连接只关运行时连接」），但当前 UI 的展开入口会先要求连接（`nav_view.rs` 的"未建连则先建连"） |
| 8 | 列/索引/约束/例程 | 全部经 JDBC 元数据 API，覆盖完整 | 完整（对象模型） | ［验］**列 + 表/视图**已缓存；索引/约束/例程/触发器/序列**有表结构与写入代码但零调用** → 走实时内省 |
| 9 | 并发/预热 | 单连接内省，UI 线程外 | 后台同步 + 进度 | ［验］C1 `warm_schemas`（预热 schema 列表）+ C2 `prefetch_columns`（邻接预取）**已接线**；`MetadataCachePool` **本日接线**（连接复用） |
| 10 | 缓存治理 | 无（不落盘） | IDE 自动管理，用户不感知 | 显式 UI：《缓存管理》对话框（按连接查看大小 / 删除）；删除前会丢弃连接池（Windows 句柄语义） |

## 3. 本仓的三条硬约束（决定了不该照抄的地方）

1. **元数据缓存是"资产"不是"临时物"**：它按连接落在 `<RDS_HOME>/data/system/global_metadata/` 或 `{项目}/meta/connection_metadata/`，**永不自动删除**（设计 §5.2）。因此必须能回答"这个文件是谁的、能删吗、删了会怎样"——这是 DBeaver（不落盘）不需要操心的事。
2. **要服务的不止导航**：mock 导入列结构、生成 SQL 的列模板都读同一份缓存。所以缓存记录的是**驱动层结构**（`SchemaObject`/`ColumnDetail`），不是"UI 节点"。
3. **单进程 + 项目锁**：同一项目同时只有一个实例（`project.lock`），这让"每连接一个 SQLite 文件 + WAL"成为安全选择；换成多实例并发写同一缓存文件，就必须像 DataGrip 那样处理跨进程一致性。

## 4. 缓存侧补齐了什么（2026-09-17）

| 项 | 之前 ［验］ | 现在 |
|---|---|---|
| **L1 内存缓存** | 只有"连接断开时失效"被调用，**从没有写入方** → 恒空；每次读都要重新走 L2 的 `open` | 补齐读写：命中即返回；**L2 命中与实时内省都回填 L1**；`fresh`（刷新）跳过并清空该连接的 L1（4 个测试，用"空连接管理器"反证命中） |
| **L2 连接复用** | 每次缓存访问都 `MetadataCacheManager::open()`：开文件 + 5 条 PRAGMA + 一次迁移校验 | `MetadataCachePool` 接线：**每缓存文件建池一次**（建池时完成迁移与预热），之后取用零校验；守卫 RAII 归还（4 个池测试 + 1 个接线证明测试） |
| **删除安全性** | — | `MetadataCacheManager::delete` 先丢弃池再删文件（否则 Windows 上句柄占用导致删除失败） |
| **表/视图分键** | L1 的 `Views` 键枚举早已存在，但**没有 getter/setter** | 补齐：一次实时内省把表与视图两半都写进 L1，展开另一半也不再查库 |

**语义收敛**：设计文档写「手动刷新 → 清 L1；L2 标记 stale（不删 L2）」，而实现是 `fresh=true` 时**删该 schema 的 L2 行再重写**（`database/src/cache.rs:10-11`）。两者对用户可见行为一致（都以实时内省为准），但**措辞不一致**：以实现为准（"先删后写"能保证不残留已删对象），建议后续把文档改为该口径。

## 4.5 导航侧分页消费（2026-09-18）

索引有数据之后，这一批把「大 schema 不再一次拉全」接到树上（C4 的数据侧 + UI 侧）：

| 层 | 落了什么 | 关键理由 |
|---|---|---|
| `engine` | `get_tables_chunk` 泛化为 **`get_objects_chunk(conn, schema_id, object_type, offset, limit)`** | 原实现把 `object_type='table'` 写死在 SQL 里，**视图文件夹根本读不到索引**；两者除类别外完全一致 |
| `database::cache` | `NavCache::object_counts` / `objects_chunk`（读侧包装） | 分类别的空结果语义集中在一处：计数全 0 或该类别无行 ⇒ 不可用，由调用方回落实时 |
| `database::navigator_service` | `NavPage { nodes, total, offset, has_more }` + `load_children_page` + `index_page` | 客户端分页必须知道**真实总数**（仅凭已加载条数推算不出“还有没有”） |
| `database::nav_jobs` | `Job::LoadChildren` 带 `offset/limit`；`enqueue_load_page`（首批 = `enqueue_load`） | 后台单线程串行，分页只排队、不阻塞 UI |
| `database::nav_view` | `child_total` 簿记；「加载更多（余 N / 共 M）」按 `offset` 取下一页、「显示更多」只放大渲染窗口；追加按 key 去重 | 取数与渲染是两件事：能显的条数上限（`page_limit`）≤ 已加载数 ≤ 总数 |

**五条设计口径（都有测试锚住）**

1. **阈值 500 分界**：对象数 ≤ 500 走既有「L1 全量」路径（命中是内存拷贝），> 500 才走索引分块；阈值以下行为不变 ⇒ 零回归风险。
2. **大 schema 不进 L1**：L2 命中与实时内省两侧都有同一道门禁——万级对象的 `Vec<SchemaObject>` 若驻留进程内，等于把省下的内存又请回来；这类 schema 下一次展开本来就按索引分页，不读 L1。
3. **`fresh` 一律不吃索引**：刷新以实时内省为准（索引是刷新前的旧值），由 `index_page` 的第一道判断拦住。
4. **索引陈旧能自愈**：翻到空块就把「总数」收敛到已加载数，否则「加载更多」会永远挂在树上、点了没反应。
5. **文件夹计数只信「表」那一个**：索引重建挂在表文件夹那趟，而视图是**另一趟**才写进 L2 的（先展开表、以后再展开视图）——那一趟不重建索引，照 `view_count = 0` 判定会让**视图文件夹整支从树上消失**。故只有表用索引计数，其余类别仍走全量收集（这一条由单测钉住）。

**验证手法**（沿用本模块的“空连接管理器”反证法）：
连接管理器为空 ⇒ 任何真正的实时内省必然失败；因此「分页返回 Ok」本身就证明这一页是从 L2 索引/规范化表取的，**没有回源库**。
6 个新测试（加 2 个纯函数测试）：首屏只取一页、第二页与首屏不重叠且末页 `has_more=false`、**视图文件夹同样能分页**、小 schema 全量无余量、`fresh` 下索引不可用、大 schema 不驻留 L1、文件夹计数来源、追加去重。

**仍缺（属搜索的下一档，不属分页）**

- 搜索框只筛**已加载**节点：~~`metadata_index` 已经能按名称检索，但导航搜索未接它~~ → **已接**（2026-09-18，见 §4.6）。内容档（注释 / 数据类型）已接在 **Quick Open 的 `#` 档**（见 §4.7）；仍缺的是**搜索结果在树中定位**。
- 索引没有 `comment` 列，分块行不带表注释（导航树今天不渲染注释，故无可见差异；属性面板走实时/规范化表，不受影响）。
- 翻页用 `LIMIT/OFFSET`：大 offset 成本随 offset 线性上升；真要刷到第 5 万条时再换 keyset 分页（按 `object_name` 游标）——今天的交互（点「加载更多」）不会跳那么深。

## 4.6 搜索档位：名称档（2026-09-18）与内容档（2026-09-19）

搜索分两档，**由 UI 入口决定**（导航面板搜索框只走名称档；Quick Open 的 `#` 前缀走内容档）：

| 档 | 状态 | 数据源 | 匹配 | 入口与门槛 |
|---|---|---|---|---|
| **名称档** | ✅ 已接（2026-09-18） | `metadata_index`（表 / 视图 / schema / 列，分页在用的同一份） | 中缀 `LIKE`（`ord` 能命中 `order_items`），大小写不敏感，通配符转义为字面量 | 导航面板搜索框 + Quick Open 默认档；【2】字符起 |
| **内容档（全文）** | ✅ 已接（2026-09-19） | `metadata_fts`（FTS5，**迁移 011：存内容 + `tokenize='trigram'`**） | 子串 `MATCH`；内容 = 名称 + 注释 + 数据类型（**不含源码定义**） | Quick Open 的 `#` 档；【3】字符起（不足一个 trigram 必然无命中） |

**为什么先接名称档而不是内容档**（当日的三条实测事实，不是偏好）：

1. **写侧成本**：旧的 `sync_fts_index` 是**连接级全量重建**（先 `DELETE FROM metadata_fts` 再 `INSERT ... SELECT` 全连接对象）。挂在“内省完一个 schema”后面，为一个 schema 付的是整个连接的代价；
   而 `metadata_index` 的重建是本 schema 级的（`rebuild_schema_index`），且已接线。
2. **匹配语义**：用户敲 `ord` 期望看到 `order_items`（中缀）。当时 FTS5 用默认 `unicode61` tokenizer，只做整词 / 前缀。
3. **消费场景**：当日搜索的真实用途是“找到那张表”，而不是“找出哪个对象的注释里提到 X”。

**接内容档时修掉的两个硬伤**（2026-09-19 实测，探针见引擎的 FTS 测试）：

1. **旧写侧引用了一张不存在的表**：`sync_fts_index` 的「视图」插入读 `views`（`v.view_name` / `v.view_comment`），而迁移里只有 `view_definitions`
   （视图注释实际在 `tables.table_comment`）——即使被调用也会在视图那段报 `no such table: views`。
   现由 **`rebuild_fts_schema(schema)`** 接管（按 `tables.table_type = 'VIEW'` 与 `routines` 取数，schema 级幂等重建），并挂在 `rebuild_schema_index` 同批；
   **它失败只告警**：名称档与分页靠的 `metadata_index` 不受牵连。
2. **旧表是 contentless，读不到身份**：`content=''` 时 `MATCH` 能命中，但 `SELECT` 出来的 `search_type` / `object_name` / `parent_name` 全是 NULL
   （`Invalid column type Null`），`snippet()` 也无从生成——整条读路径其实不可用；且 `unicode61` 把连续中文当一个 token（注释里搜“渠道”0 命中）。
   迁移 011 改为**存内容 + trigram**（中文注释需 ≥ 3 字；索引体积增重约 3 倍，元数据文本短，可接受）。

> 教训（与本文档一贯口径一致）：未验证的代码里藏着的不只是风格问题——这两条都不是“没人调”，而是“调了就错”。

**实现要点（都有测试锚住）**

- 名称档引擎：`MetadataCacheOps::search_index(conn_id, needle, limit)` —— 联结 `schemata` 拿到 catalog / schema 名，排序按「相等 → 前缀 → 其余」+ 类别权重（表 > 视图 > schema > 列）+ 名称；
- 内容档引擎：`MetadataCacheOps::search_fts(query, type)`（trigram 子串；返回身份 + `snippet()` 的 `<mark>` 片段）+ `rebuild_fts_schema`（写入侧，schema 级）；
- 视图：查询词变化才排队（同一词不重搜）；结果按查询词丢弃**过期批次**；无缓存的连接**不建文件**（`cache_file_exists` 先查路径）；
- 导航面板结果区在树顶，与本地过滤**共存**：本地过滤命中已加载节点（零往返），索引搜索补上尚未展开到的那部分；单击命中 → 开属性面板（“还没展开到那层也能看结构”）。
- **引用统一**（2026-09-19）：命中 → `engine::ObjectRef` → 属性定位走 `database::model::property_ref_of`；
  Quick Open 的元数据行键改用 `ObjectRef::key()`——它之前自拼「连接 + 种类 + 父对象 + 名字」，**不含 catalog / schema**，
  `sales.orders` 与 `archive.orders` 会撞成同一个键（选中跟错行）。

**仍缺**：**源码**（定义文本）搜索（FTS 只收名称 / 注释 / 数据类型）、结果“在树中定位”、按对象类别的 facet（今天只能按连接 facet 缩小范围）。

**方向（已拍板，2026-09-18）**：搜索与命令这类“先输入再选”的交互**独立成一层**
（类 VS Code 的 Quick Open / 命令面板，同时容纳命令入口）——已落地在 `workbench/src/quick_open/`；
导航面板里的那份是「够用」版，新特性加在 Quick Open 那一侧。

## 5. 仍然差什么（按"对 10 万表体验"的贡献排序）

| 优先级 | 缺什么 | 影响 | 触发条件（什么时候必须做） |
|---|---|---|---|
| **高** | ~~`metadata_index` + `get_tables_chunk` 分页~~ | 今天大 schema 会一次拉全；10 万表库的树首屏与内存都会顶到设计之外 | ✅ **已全线接通**：索引写入侧（2026-09-17）+ 分页读与 UI 消费（2026-09-18，见 §4.5）；首屏只取一页、按 `offset` 追加、大 schema 不入 L1 |
| **高** | ~~写入侧顺带写索引~~ | 上一条的前置：索引表恒空，接了读也读不到 | ✅ 已接（同上）；顺带修了一个真缺陷：`metadata_index` 不在外键级联链上，删 schema 会留孤儿行（测试抓到） |
| **中** | ~~`IntrospectionLevel` 接线~~ | 大库可以只拉名字、把列留到展开时取 | ✅ **已接**（2026-09-17）：实时内省后按对象数自动定级并登记到连接；“是否预取列”据此门禁（Level1 / >3000 对象不预取）+ 3 个测试 |
| **中** | ~~FTS 内容搜索（写侧 + `search_fts`）~~ | DataGrip 级"全库搜"体验的第二档 | ✅ **已接**（2026-09-19）：`rebuild_fts_schema`（schema 级，挂在 `rebuild_schema_index` 同批）+ 迁移 011（存内容 + trigram）；消费方 = Quick Open 的 `#` 档（≥ 3 字）。修掉两个硬伤：旧语句引用不存在的 `views` 表、旧表 contentless 读不到身份（见 §4.6）。**仍缺**：**源码**（定义文本）搜索 |
| **中** | 搜索结果“在树中定位”（展开到该对象并高亮） | 今天搜到对象只能开属性面板，不能一键把树展开到它那一层 | 用户把搜索当主要入口时；靠 `ObjectRef::key()` 与树节点 key 同构，已具备实现基础 |
| **低** | 增量同步（快照 + 变更检测） | 大库重复内省时只拉变化；今天是整 schema 重写 | 内省耗时成为主要抱怨时 |
| **低** | 身份指纹键（`meta_{fp}.sqlite` + 引用计数） | 同一物理库多连接共享缓存；改名/改密码不重建 | 连接数量增长、出现"同一库连了三次"的抱怨时 |
| **低** | L1 覆盖索引/约束/例程等其余 9 类键 | 这些类别今天完全走实时内省（L1/L2 都没有） | 属性面板成为高频操作时 |

**关于剩余的增量同步 / 身份指纹键：有意不动。**

理由是本模块自己的历史教训：它积压了 ~150 项“写完了但没人调用”的代码，根因就是**先写实现、后找消费者**。
这两项在 UI 上还没有消费者，现在只补写入侧只会再造一批“写了没地方用”的表与代码——
**接一个真实消费者，再写它需要的那一半**（FTS 就是这条路走通的正例：等到了 Quick Open 的 `#` 档才接线）。

## 6. 结论：该学什么，不该学什么

**该学（DataGrip 取向）**
- **持久化 + 内省级别**：本仓已经选对（持久化），缺的是内省级别的接线——它是"大库不卡"的第一道闸，成本极低（注册表与阈值都写好了）。
- **搜索走缓存**：DataGrip 的 Search Everywhere 不查库，这种"本地可搜"体验与本地优先产品气质一致，值得作为差异化。
- **断连可浏览**：本仓的 L2 保留设计已具备条件，但 UI 入口仍是"未建连先建连"，白白浪费了这个能力。

**不该学（DBeaver 取向的教训 / 也可能反过来）**
- **不要照搬"会话内不落盘"**：DBeaver 的选择服务于"连接即一切"的轻量模型；本仓有多处（mock / 生成 SQL）需要在**没有活跃连接**时也能取到结构。
- **不要为了缓存引入"第二套真相"**：DataGrip 的本地模型与库结构之间需要同步语义；本仓的作法是**缓存只存"上次从驱动读到的事实"**，判断"是否过期"只靠 `fresh` 与 TTL，不做结构 diff（diff 属增量同步，见 §5）。

**底线判断（本仓现状，2026-09-19 更新）**
> 今天能保证：**小库（数百对象）秒开** —— L1 命中进程内、L2 命中不重开文件、刷新语义清晰、缓存可管理。
> **大库的取数与“找到它”都通了**：首屏只取一页（`metadata_index` 分块，表/视图各自分块）、「加载更多」按 offset 追加、大 schema 不驻留内存；搜索两档都接上了——名称档（中缀，导航面板与 Quick Open 默认档）与内容档（trigram，注释 / 数据类型，Quick Open `#` 档）。
> 还不能保证：**源码（定义文本）搜索**与**结果定位**（搜到的对象不能在树里展开并高亮）；大 schema 里第 500 名之后的顺序是按名称升序（与索引一致，不同于源库原始顺序）。
