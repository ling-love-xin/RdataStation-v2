01

为什么它不再是一个 Textarea

四处「看着有、实际是假」的底座，逐条换成了真东西
旧样子（V1）现在
只有一个 Textarea：无高亮、无补全、无多文档、无状态栏 组件库编辑内核 + 语义高亮（写不完的 SQL 也能着色）+ 补全（打字 / Ctrl+Space / 模板）+ 多标签 + 真实状态栏 + 大文件档位降级
执行内联在 render 闭包里，同步直连全局分析库文件 后台工作线程 + 主线程轮询回填；渲染路径零 I/O；执行走驱动与连接，与「当前活动连接」不再冲突
一次抓取 + 上限截断：亿行级表上不可用 分段抓取 1,000 行/段 + 滚到底自动续取 + 未知总数显示 N+；导出区分「仅已抓取 / 抓全量后导出」
格式化是 format!("{:?}", stmt)——输出不是 SQL sqlglot generator + 按语句区间原位回填：注释、空行、没写完的半句一个字节不动
02

三个高光

如果只记三件事
HIGHLIGHT 1

「这条 SQL 发到哪」是文档属性，不是运气

源库 / 本地加速 / 联邦三档互斥、随文档持久化。跨重启连的是同一条连接、同一个通道； 通道失效会回退并说明原因，而不是静静换一个库接着跑。

源库：可写 · 有事务加速：只读挂载 · USE 后不写限定名联邦：别名.schema.表
HIGHLIGHT 2

结果不是终点，是可以继续算的一张表

本地筛选（只动视图）、下发源库重查（拼 WHERE 去 LIMIT）、排序下发、右键按值筛选、 丢给本地 DuckDB 做聚合、右键洞察此列、导出成 Parquet / Excel——每一步都产生新结果集或落到别的面板，原结果一行不动。

筛选 300ms 防抖分析上限 20,000 行并如实说明导出跟随筛选洞察不物化结果集
看七条出口 ↓
HIGHLIGHT 3

每一句「做不到」都带着原因

报错能定位到出错的那个词（10 类真实错误文本，认不出就不给位置）、通道不可用写清差哪一条、 EXPLAIN 支持不了的方言直接回绝、事务内的语句取消不了也如实说明—— 按了没反应在这套界面里是不允许的。

错误卡片 + 定位 + 复制原文状态栏永远说真话

结果区
中断与超时：状态栏 ■ 中断 + 耗时累加；批量里剩余语句标「已取消」且不再发给驱动。超时按连接的 query_timeout，没配就是没有超时（不造默认值）。
事务：真的会话状态（走驱动 API，不是拼 BEGIN 字符串）；状态栏 TX 区显示开启时长 + 提交 / 回滚 + 自动提交开关，状态随执行结论一起回来。事务内的语句暂不可取消 / 无超时——驱动 Transaction trait 没给入口，如实记在案。

三档执行通道

互斥 · 随文档持久化 · 边界写在界面上
通道怎么跑能力边界界面上看得见的部分
源库直连驱动（四类库 · 六条实现路径） 可写 · 有事务 · 数据实时 状态栏连接段 ●P·orders · 结果集徽标「源库」
本地加速DuckDB ATTACH … READ_ONLY + USE，不写限定名也能查 只读 · 无事务 · 表清单在 ATTACH 时定型（新表要重挂） 菜单行尾写清不可用原因 · 「重新挂载源库」 · 写语句双保险拒掉
联邦一台 DuckDB 挂多个源，跨源写 别名.schema.表 只读 · 无事务 · 只给已挂上的源 补全按别名限定 · 历史带参与源 · 挂不上的源点名给原因
门控是真值：连接开关 → 驱动类型 → 扩展可用性 → 运行时就绪，按「谁能先改」的顺序只报第一条过不去的；扩展没试过不拦（首次执行时在工作线程装一次），试过且失败就把原话记下来显示在菜单行尾。

结果区 · 编辑器的下半屏

网格是组件库的原生能力，我们只补它没有的那几件

◇原生就有（不手搓）

  • 虚拟滚动 · 行 / 列 / 单元格选择
  • 列宽拖拽 · 列序移动 · 冻结列
  • 点列头排序（三态循环）
  • 滚动到底自动加载
  • 右键菜单 · 单元格自定义渲染
能力台账写在 view/results/mod.rs，避免后人再手搓一遍

＋我们补的

  • 本地筛选：任一单元格子串命中，300ms 防抖，只动视图层
  • 下发源库：拼 WHERE 重查 → 新结果集，去掉原 LIMIT 并提示
  • 排序下发：按点的那列到源库排（不 CAST，让源库按自己的类型排）
  • 右键：按值筛选 · 复制此值 · 升 / 降序下发 · 冻结列 · 洞察此列

◈结果集本身

  • 上限 5 份，淘汰最旧的未选中项（在看的那份不会被挤掉）
  • 标签带通道徽标；切通道后旧结果标灰 + 顶部提醒
  • 工具栏左段带来源摘要：原查询 / 下发筛选 / 排序下发 / 取下一段 / 分析 / 执行计划
  • 失败带红点，错误卡片给定位与复制

⤓导出五档

  • CSV（RFC 4180）· JSON · INSERT（每 200 行一条）
  • Parquet / XLSX 经 DuckDB COPY，一次性线程 + 回执
  • 两档范围：仅已抓取 / 抓全量后导出（失败不落半截文件）
  • 筛选中导出的是筛后的行集，回执里明示
Parquet 离线可用（内核自带）；XLSX 首次要装 excel 扩展，写时显式带表头

↕编辑区 / 结果区

  • 可拖拽分栏（组件库原生，不手搓拖动条）
  • 下限 112px、上限 768px：不会把编辑区压成 0
  • 没有结果时结果区不占位

⚑一个例子：筛选到底改了谁

筛选与排序都只改「视图行序」，数据行一行不动：清掉筛选立刻恢复原状，已抓到的窗口不会被搞乱，行号列显示的是视图行号。

换结果集时排序不继承（列都可能不是同一批），筛选词留着（你还在找同样的东西）

结果集是一条产线 · 七条出口

除了看，它还能被继续用——每条出口都落成新结果集或别的面板

结果集不是“查询的尾巴”，而是编辑器里的一等公民：有标签条、有通道徽标、有来源摘要、有上限淘汰。 它的状态就是文档状态的一部分——所以这些衍生能力全部长在同一个 crate 里，不跨 crate 传两遍。

☰菜单是纯函数算出来的

context_menu_items(值, 列名, 列序, 是否冻结, 能否洞察) 返回该摆哪几项、每项叫什么、点下去干什么—— 界面只负责画，所以每一项都能单独断言。

  • 短预览就地折叠：空白折叠 + 超 24 字截断，长值不把菜单撑开
  • 升 / 降序标注了“下发源库”——它真的会重查，而不是改本地顺序
  • 能力没有就不摆入口：「洞察此列」只在能洞察时出现，与「按值筛选」同口径
纯函数在 view/results/grid.rs；网格只负责说“用户点了谁”，SQL 与连接是面板与宿主的事
出口你做什么落到哪
① 看虚拟滚动 · 列宽 / 列序 · 冻结列 · 单元格 / 行 / 列选择 · NULL 斜体组件库原生，零手搓
② 筛工具栏筛选框，任一列命中即可；300ms 防抖，只动视图同一份结果，行号列改显视图行号
③ 排点列头（本地三态循环）· 右键升 / 降序（下发源库，不 CAST）本地排序原地；下发排序落新结果集
④ 回源库再问一遍▢ 下发源库 打开后应用筛选：拼 WHERE 重查（去掉原 LIMIT 并提示）新结果集，原结果一行不动
⑤ 二次分析⚗ 分析 ▾：计数 / 按列分组（最多 8 列）/ 自定义聚合 SQL（{table} 指这份数据）本地 DuckDB → 新结果集（见下一节）
⑥ 洞察右键「洞察「列」这一列」：把列交给洞察面板做画像洞察面板（不物化结果集，见下）
⑦ 带走⤓ 导出 ▾：CSV · JSON · INSERT · Parquet · XLSX；两档范围落盘（后台写 + 回执），跟随筛选
洞察为什么“不物化结果集”：洞察拿到的不是这份结果的数据副本，而是 「这一列 + 产生它的 SQL + 在哪条连接上」，由洞察侧重跑一句带 LIMIT 500 的取样落到自己的临时表里。 这样就不需要建 tmp_q_* 表、也就没有“结果集被丢弃时回收临时表”那套生命周期。 代价写在案上：列类型不在这里猜（编辑器手里只有字符串化的行）——目标头在数据回来前只显示来源，不显示类型；编一个“看起来像真的”类型更糟。
值查看 · 今天的形态：值在菜单里就地短预览（折叠 + 截断）+「复制此值」； 完整的值预览弹层与值编辑还没做——台账写在 view/results/mod.rs： 组件库没有原生 filter / 值预览 / 值编辑，这三件（连同洞察入口）属于业务语义，各有计划步骤，落地时加新文件而不是往 grid.rs 里堆。

三条口径：① 分析的对象就是眼前这份数据——源库断了、慢查询不想再跑，照样能分析；② 值按展示文本进库，列类型由引擎按整列推断（数字列在 Parquet / XLSX 里就是数），代价是 007 这类前导零会按数字落；③ 临时表由 TempTableManager 登记（上限 / TTL / 切项目清场），不泄漏。
09

编辑体验

能借组件库与内核的一律不手搓；自己写的部分都是纯函数 + 可逐条断言
能力关键点
高亮sqlglot tokenizer → 字节区间 → 主题语法色；写不完的 SQL 也能着色（语法树会失败，词法不会）
补全打字即触发（标识符与 .）；候选来自导航侧 L2 缓存（后台预载、内存读）；Ctrl+Space 手动请一次，与打字那条完全同一份候选
限定名按通道：源库 / 加速 schema.表，联邦 别名.schema.表（只给已挂上的源）；未绑定连接不给候选（不猜）
模板片段6 条内置（来自模板库），插到光标处并选中 {table} 占位符——接着敲表名就直接覆写
格式化Ctrl+Shift+F，选区优先；区间原位回填：注释 / 空行 / 没写完的半句一个字节不动
转译10 个目标；先切分再逐条——脚本一条不丢（整篇接口会静默丢第二条，这条缺陷被对照测试钉住）
执行计划按通道取方言（加速 / 联邦用 DuckDB 的）；落新结果集贴「执行计划」标题；SQL Server / Oracle 如实回绝
查找 / 替换内核已绑并有 listener，界面由组件库渲染——应用层零自建、不重绑
九条已注册的快捷键（键位在 crates/app，context editor）：Ctrl+S 保存 · Ctrl+O 打开 · Ctrl+Shift+S 另存为 · Ctrl+Enter 执行（选区优先）· Ctrl+Shift+Enter 执行全部 · Ctrl+Space 补全 · Ctrl+/ 行注释 · Ctrl+Shift+F 格式化 · Ctrl+W 关闭（脏则三态确认）。没有注册的一律不宣传。
10

报错与定位

诊断 · 定位 · 聚焦，三件事分开做

⌖位置从哪来

  • PG 两条驱动路径的结构化 position（1 基字符 → 字节偏移，越界返回 None 而不是钳到末尾）
  • DuckDB 的 LINE n: + 插入符 · SQLite 的 at offset N · MySQL 的引号词
  • 共覆盖 10 类真实错误文本；认不出就不给位置——定位错比不定位更糟

▣包装查询会被还原

  • 分段抓取会给语句套 LIMIT/OFFSET 外壳；报错里的位置是相对外壳的
  • 引擎把它还原成你的原句：位置平移回去，回显 SQL 换回原文
  • 落在包装上的位置宁可不给——给错位置会让人怀疑自己的 SQL
11

历史 · 会话 · 闸门

三件「跨时间」的事

⟲历史面板（右 Dock）

  • 字段是真的：耗时 · 成功 / 失败 · 原因 · 返回与影响行数 · 绑定连接 · 执行通道与参与源
  • 搜索 / 重放（只打开到编辑器，不替你执行）/ 删除 / 清空
  • 刷新靠版本号，渲染路径零 I/O

◷会话持久化

  • 内容 · 光标 · 选区 · 模式 · 执行通道 · 连接绑定
  • 未命名文档不存（重启认不回来）；存的是内容，不重读磁盘
  • 通道失效 → 回退源库并说原因；连接不在列表 → 回退「跟随当前连接」并点名
真 SQLite 上跑通：关文档 → 重开 → 六项都回来

🔒写入闸门

  • 项目只读：写语句在提交前就被拒（要改数据先解锁项目），SELECT 照跑
  • 加速 / 联邦拒写源库，但允许本地临时对象（会话变量）
  • 编辑器只读与连接只读是两个独立维度，状态栏分开写
12

架构 · 依赖只向下

编辑器不认识「项目 / 连接 / 文件对话框」——一律走端口注入
应用层
rds-app：窗口 · 主题 · 键位注册（九条编辑快捷键都在这）
宿主（工作台）
rds-workbench：把端口接到真实世界——执行器 · 连接列表与建连 · 通道门控 · 补全目录 · 项目锁 · 会话存储 · 系统文件对话框（rfd 只在这）
编辑器 crate
rds-editor：模型与纯函数（completion · analysis · export · format · translate · edit · diagnostics · history · channel · limits · mode）+ 视图（宿主面板 · 结果区 · 对话框 · 补全适配 · 状态栏）
引擎 / 数据
rds-engine：驱动与会话 · 事务 · 取消与超时 · DuckDB（分析 / 加速 / 联邦 / 扩展目录）· 历史与模板库 · 元数据缓存 · sqlglot 原语（切分 / 格式化 / 转译 / 执行计划 / 高亮）
基础
gpui-kit（视图唯一依赖）· shared · paths（数据根 / 扩展目录）· database（导航缓存）
依赖方向app → workbench → editor → engine → shared / paths· editor 不依赖 workbench（能力走端口）

◎端口清单

  • QueryRunner 执行 / 中断 / 取段 / 下发 / 分析 / DuckDB 导出
  • ConnectionsPort · ChannelsPort
  • CompletionPort（目录 + 模板）· SessionStore
  • ProjectPort · HistoryPort · 路径选择器
未接端口一律如实报「未接入」，而不是静默失败或假装可用

◑两条纪律

  • 渲染零 I/O：渲染路径只读内存快照；加载 / 执行 / 内省全在后台线程 + 轮询回填
  • 纯函数优先：候选挑排、导出编码、血缘摘要、诊断解析、格式化计划……逐条断言
  • 视图不出现裸 px()（尺寸进常量表）、不出现裸色值——契约测试守着

▦为什么是独立 crate

  • 编辑器有自己的状态与生命周期，独立才谈得上「无宿主可测」
  • 结果区不另建 crate：它的状态就是文档状态的一部分，拆出去只会跨 crate 传两遍
  • 判定标准（有状态 / 有视图 / 依赖方向）写在架构文档里

◈真机探针（需要环境变量，缺了就跳过）

  • editor_exec_real：六条驱动路径的取数、影响行数、错误定位、执行计划
  • duckdb_accel_probe：只读挂载 · 未限定名 · 实时性 · 写拒绝
  • duckdb_export_probe：Parquet 往返（离线必过）· XLSX 写出 + 读回
  • federation_probe / federation_credentials_probe：跨源查询与凭据脱敏
  • sqlglot_capabilities：十项能力台账（含把缺陷钉住的对照测试）
  • transaction_affinity · oracle_probe：会话亲和性 · Oracle 接入结论（扩展 / 凭据 / 只读边界）
另有一组不需要环境变量的真机回归：editor_session_real.rs（真临时 SQLite，4 项）

⌖真机抓出来的真缺陷（都已修）

  • PG 的结构化位置是相对包装查询的 → 光标偏 16 字节
  • EXPLAIN 被分段窗口包进子查询 → MySQL 1064
  • duckdb-rs 的 column_name 在 prepare 后调用直接 panic
  • XLSX 不传 HEADER 就不写表头（首行被当成列名）
  • PG COMMIT 永远等不到响应（sqlx runtime 挂错线程）
每条都写进「已知问题」清单，带着现象与修法

边界 · 这些事它不做

把话说在前面，比事后解释便宜

✕明确不做

  • 结果集不内联编辑：行内改值 + 写回源库属表格能力（M4）——避免「结果集」与「表数据」语义纠缠
  • 不替用户执行历史里的语句：重放只打开到编辑器
  • 不做语义分析型补全：前缀 + 上下文判据，不猜「你想写什么」
  • 不静默联网：装扩展只发生在明确的动作里，失败把原话与目录一起说出来

◷还没做的（都记在册）

  • 值预览弹层 · 值编辑（要行标识）
  • 只读锁 ⓘ（连接侧写策略；「提醒后放行」那一档）
  • CSV / JSON 的列类型化输出 · 结果血缘落库
  • 候选超过 60 条的翻页
  • 分析模式笔记本视图（Phase 1c）
  • SQL Server 真机探针 · 事务内语句取消 / 超时（驱动限制）
