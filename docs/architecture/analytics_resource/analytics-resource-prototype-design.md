## 1. 设计基准

| 项 | 取值 | 来源 |
| --- | --- | --- |
| 面板位置 | 左 Dock（活动栏第 3 项） | `workbench/src/view.rs:35-44` `LeftPanel::Resources` |
| 面板宽 | 起步 15rem = 240px，可拖拽 | `ui::LEFT_DOCK_WIDTH` |
| 详情面板 | 编辑区右侧，默认 20rem，范围 13.75–47.5rem，**宽度记忆存 `settings.json`** | `ui::PROPERTY_PANEL_*`（沿用 M4 决策 3） |
| 行高 | 1.5rem = 24px（与 M4 树 / M5 列表一致） | `ui::ROW_HEIGHT` |
| 面板头高 | 2.25rem = 36px | `ui::PANEL_HEADER_HEIGHT` |
| 契约 | 零裸色值 / 零裸 `px`；组件不手搓；render 期零 I/O | `../ui/ui-design-spec.md`、`.agents/skills/rds-ui-spec/SKILL.md`（仓库根相对，下同） |

**三条界面原则**（由语义裁决推出，不是审美偏好）：

1. **复现强度必须可见**：`已归档`（强）/ `分析表`（中）/ `引用`（弱）在列表行与详情面板都要常显 —— 用户必须一眼知道"这东西半年后还打不打得开"。
2. **本体与显示名分离**：`name` 是显示名（可改），`file_rel_path` 是物理路径（归档时定，**不随重命名变化**）。改显示名不动文件，避免破坏外部引用与 git 历史。
3. **只读是常态**：存档本体不可写。要改 → 走"取回"（检出）。面板上不提供"编辑资源"入口（有入口就一定有用户点了才发现不能存）。

### 2.1 面板头（高 2.25rem）

| 元素 | 规格 | 行为 |
| --- | --- | --- |
| 标题 | `text_sm` + 中等字重；前缀图标 `icons/chart-column.svg` | 点击 = 折叠/展开（沿用 M4/M5 面板头行为） |
| `＋ ▾` 主操作 | `CONTROL_HEIGHT_SM` 紧凑按钮 | 菜单两项：**从草稿箱归档…**（打开草稿多选对话框）/ **从本地文件归档…**（系统文件选择） |
| `⋯` 更多 | 同上 | 重建索引… / 打开资源目录 / 回收站… / 刷新 |

> **为什么主操作不是"新建存档"**：存档的本体必须来自某处（草稿 / 本地文件 / 分析表），**不存在凭空创建的存档**。这与 v1"填 JSON 建资源"的入口形成对照——v1 正是因此没人用。
>
> **落地现状（2026-09-17，两批，2026-09-18 补一笔）**：`＋ ▾` 两项已落（**从草稿箱归档…** 走草稿多选对话框：单选→完整确认、多选→默认名批量；**从本地文件归档…** 走系统文件选择）；`⋯` 四项**均为真实现**（**重建索引…** 与状态行「修复…」同一条路、**打开资源目录** 用系统文件管理器开 `resources/`、**回收站…** 开回收站对话框（P0.8 已落）、**刷新** 与切换项目同一条取数路径）；标题前缀图标已落。**标题点击折叠/展开未落**：M4/M5 面板头由 Dock 的 tab 呈现、不自绘，单独给 M6 会让同一个动作只在一处可用——等“自绘面板头统一”那一批一起做。**草稿箱右键**那个入口属草稿箱 crate，仍未接。

### 2.2 工具栏（高 2rem）

| 控件 | 规格 | 说明 |
| --- | --- | --- |
| 搜索框 | 高 `CONTROL_HEIGHT_SM`，占满剩余宽 | 匹配 **显示名 / 别名 / 标签 / 来源表**（不再只 `LIKE name OR alias`）；`Ctrl+F` 聚焦；`Esc` 清空 |
| `筛选 ▾` | 紧凑按钮 + 弹层 | 三维：**kind**（文件 / 分析表 / 引用）、**强度**（已归档 / 分析表 / 引用 · 可"仅显示可能失效"）、**标签**（多选 · **已落，见下**） |
| `排序 ▾` | 紧凑按钮 + 弹层 | 名称 / 归档时间 / 更新时间 / 大小 / 版本号；箭头上再点翻转（沿用 M4 与 v1 `use-pagination` 语义）。按钮上显示当前字段 + 箭头（四个字的字段在按钮上用两字短名：归档 / 更新） |

> **落地现状（2026-09-18，第四刀）**：**五个排序键已全部落地**（`filter::SortField::ALL` 就是菜单顺序的单一来源）。与规格的一处补强：比较的是**行上的原始值**（时间戳 / 字节数）而不是尾巴里格式化过的字符串（`1.2 KB` vs `900 B` 会得出错误顺序），且**缺值（无体积 / 无归档时间）在两个方向上都排最后**——“不知道”不该在降序里冒充“最大”。为了「大小」不是空功能，归档 / 再归档 / 版本还原 / 补登 / 接受当前内容这五条路径都在写指纹时同批登记本体字节数（`PayloadStore::file_size`）。按钮文案用两字短名（归档 / 更新 / 版本），**四个字的全名留在菜单里**——按钮要跟搜索框抢 240px 面板的宽度。
> **排序会被记住（2026-09-18，第六刀）**：面板里点一次排序就写回设置 `resources.default_sort`，下次打开项目还是这一列（“默认排序” = 上次用的那个，不另给一份设置）；只存**字段**不存方向，方向按字段惯例（名称升序，时间 / 大小 / 版本降序）。
> 搜索框的**匹配面已按规格到齐**（2026-09-20，第十一刀）：显示名 / 别名 / 标签 / 来源表 + 尾部字段，**大小写不敏感**。与规格的一处补充：**匹配面比展示面宽**（别名 / 标签 / 来源表行上不显示，面板只有 240px）——与 quick_open 的 `keywords` 同口径：**可搜、不高亮**。字段之间留一个空格：不留的话跨字段的偶然连缀（名尾 + 尾巴首）会造出假命中。搜索范围不可见，故“搜不到”的无匹配空态会列出可搜字段（`filter::SEARCH_FIELDS` / `no_match_hint`，单一来源）。筛选菜单的**强度维**仍未单做（kind 维 + “只看需处理”已覆盖它的实际用途——强度由 kind 决定，多一维就是同一个条件说两遍）。

### 2.3 列表行解剖（高 1.5rem）

```
▤  dau_report.sql            v3   ●已归档   1.2 KB   3 天前
│  │                          │    │          │        └ 相对时间（悬浮显示绝对时间）
│  │                          │    │          └ 大小（analysis 型显示"行数 × 列数"）
│  │                          │    └ 复现强度徽标（唯一色块，见 §6）
│  │                          └ 版本徽标（v1 时不显示，减少噪声）
│  └ 显示名（text_sm）；本体缺失时加删除线 + `danger` 点
└ kind 图标：文件 / 分析表 / 引用（三档形状不同，不只靠颜色）
```

| 交互 | 行为 |
| --- | --- |
| 单击 | 选中（右侧详情面板随之切换） |
| Ctrl / Shift + 单击 | 多选 / 区间选择 |
| 双击 / Enter | **打开（只读）**：`File` → 编辑器只读模式；`Analysis` → 结果表格；`TableRef` → 先校验存在性 |
| ↑ / ↓ | 键盘漫游（含跨分组） |
| F2 | 重命名**显示名**（不重命名文件，见 §1 原则 2） |
| Delete | 移入回收站（底部出现撤销条，沿用 M5） |

> **落地现状（2026-09-18，第二刀补一笔；2026-09-20 第十三刀补齐）**：`↑/↓` 的“含跨分组”已满足——分组头也是列表的一项（它参与漫游位置但不参与选中：头被点 / 选到时面板的选中不会被改成一条分组），所以上下键会跨过分组头继续走到下一组的行。**`F2` 重命名已落**（单输入小对话框 + 行右键「重命名…」，只改显示名）。
| Ctrl+A | 全选当前分组 |
| 右键 | 见 §3.2 |

> **落地现状（2026-09-17）**：行渲染用 `list::List`（虚拟化 + 组件化 hover / 选中 / 键盘漫游），**行首 kind 图标已接**（`FileText` / `Table` / `ExternalLink`，一律 `muted`），**行内不摆常驻按钮**——动作走右键菜单（§3.2）。键鼠交互已归位：**单击=选中、`Ctrl`=切换入选择集、`Shift`=区间、双击=打开**（行自己接管点击，因为组件默认把单击也接到确认上）、`Ctrl+A` 全选可见行、`Enter` 打开、`↑↓` 漫游、`Delete` 对选择集生效。**`F2` 重命名已落（第十三刀）**；行内 hover 动作仍未做（原型把它们归给详情面板批）。
>
> **行态口径（2026-09-20，UI 收尾 / V3·V4·V8）**：①**行距钉在 `ui::ROW_HEIGHT`（24px）**——`List` 的行距是**单一值**（只量一个样本行），而 `ListItem` 自带的 `py_1` 会让每项实际 32px，现统一走 `list_row()` 压掉（窗口测试按「两个分组头之间每项正好 24px」钉住；分组头与存档行必须同形同高）；②**悬停不覆盖选中**：面板行的 hover / 选中都由组件承担（`ListItem`），版本历史行同批换成 `ListItem`（原先手搓的 `when(selected, bg) + hover(bg)` 会把选中底盖掉）；③**分组头也是列表的一项**：鼠标点、或**停在它上面按 Enter**，都能折叠 / 展开（Enter 走 `List` 自己的确认通道，不另做自绘焦点）；④可点元素一律语义控件（`Button` / `Checkbox`），不再用「文本 div + `cursor_pointer` + `on_click`」。

**字段优先级（240px 内的取舍规则）**：显示名 > 复现强度徽标 > 版本徽标 > 相对时间 > 大小。

- `version = 1` 时**不显示**版本徽标（减少噪声）；
- `File` 行：大小与相对时间合并为一个 `muted` 字段；
- `Analysis` 行：显示「行数 × 列数」替代大小；
- `TableRef` 行：显示「无指纹」替代大小；
- 放不下的信息一律省略号 + hover tooltip 补全（**不缩减行高、不做两行行**——紧凑一致性优先于信息完整）。

### 2.4 分组折叠区（替代文件夹树）

- 分组 = **单层**（`../analytics-resource-architecture.md` D8）：`全部分组` → `未分组` → 各分组。
- 分组头：左侧 2px 色条（`ui::GROUP_BAR_WIDTH`，沿用 M4 分组头做法：`primary` + 圆头 `0.875rem`）+ **展开指示**（走共用原语 `tree::disclosure_slot` + `disclosure_icon`，与 M4/M5 同一个 10px 槽）+ 名称 + **「默认」标记**（本项目设为归档默认落点的那个分组）+ 计数；折叠状态持久化（**按项目分开记**）。
- 缩进是**固定两级**（`depth ∈ {0,1}`）的局部内距（`pl_2`），**不套** `TREE_BASE_PADDING + depth × TREE_INDENT` 那条树公式（这里没有第 N 层，套了会把 depth=1 的头右移 14px）。
- 拖动行到分组头 = 移动（沿用 M4 的行拖拽形态：载荷带一批 id、落点决定语义、出口与右键菜单同一条；不做"拖到编辑器"）。
- **不做**：多级嵌套、面包屑、排序号手动调整。

> **落地现状（2026-09-18，第二 / 三 / 七刀；拖拽见第十二刀）**：**三层分区、折叠、管理入口与折叠态持久化均已落**（`filter::build_visible_items` + 分组头行 + 分组头右键菜单；色条用 `list_active_border`）——分组头与存档行一样是列表的一项（虚拟化 / 漫游 / 滚动只维护一份）；**计数从当前可见行现算**（筛选后头里的数就是眼前的行数），没分组时不出头（空库不多两行噪声）；分组头右键：重命名… / 设为|取消归档默认分组 / 删除分组（成员回未分组）/ 新建分组…（完整顺序与置灰口径见 §3.2）；**折叠态写进设置**（`resources.collapsed_groups`，按项目根分桶——分组 id 是每项目独立生成的，平铺一份列表会在“打开另一个项目”时被清掉）。
>
> **落地现状（2026-09-20，UI 收尾 / V1·V2·V4）**：①展开指示的字符载体 `▸/▾` **退场**，改 `tree::disclosure_icon`（与 M4 导航 / M5 草稿箱同一套；`tree.rs` 头注点名的「第三处」就是这里）；②色条改 `primary`（与 M4 分组头同角色，两者在 `rds-theme.json` 里明暗同值 → **零视觉变化**），几何改成 `0.875rem` + 圆头；③**停在头上按 Enter = 折叠 / 展开**（与鼠标点同一条路，走 `List` 的 `confirm` 通道）。
>
> **落地现状（2026-09-20，第十二 / 十五刀）**：**拖拽已落**（规格那条「拖动行到分组头 = 移动」）。与规格的两处补充：① 落点**只有分组头**（多选时拖一条 = 拖整个选集；拖到「未分组」头 = 移出全部分组）；② 「全部分组」是聚合头**不接落点**，而「拖到某一行」也不接——资产库没有手工排序，拖到行上会承诺一个做不到的语义。悬停高亮用 `list_active`（与选中底同 token）；只读项目不给拖；拖到当前所在分组不发请求（与菜单里当前项置灰同一口径）。
>
> **默认分组（第十五刀）**：分组头右键多了「设为 / 取消归档默认分组」，设中的那个头上有「默认」小字。它只影响**下一次归档的预选值**，不碰已有存档的归属；语义取**显式设置**（案 A，不是“跟随上次”），理由与两案对比见 `analytics-resource-dev-plan.md` §4 表末。

#### 2.4.1 分组对话框（21 页）实现复核（2026-11-07）

> 逐条对回 `dialogs/group.rs`、`resource_host/group_actions.rs`、`jobs/tag/group.rs` 与 `store/folder.rs`。

- **一个形状两个动作**：新建与重命名共用同一个对话框，形态由 `GroupNameKind::{Create, Rename{id}}`（`group.rs:24-29`）决定；提交事件 `GroupNameEvent::{Create{name}, Rename{id,name}}`（`:33-36`）。标题取 `dialog.title(title)`，`Dialog::title` 只吃一个元素（vendor `dialog/dialog.rs:402`）——**没有副标题槽**，原型旧稿的「项目「营销分析」」/「3 个存档」无实现位置。
- **四元表是这一处唯一的文案源**（`group.rs:50-60`）：Create =（「新建分组」/「分组名」/「创建」/「分组是单层的：没有子分组，也不影响存档本体」）；Rename =（「重命名分组」/「分组名」/「保存」/「只改显示名：组里的存档不动」）。
- **宽度 384px**：`.w(cx.theme().font_size * ui::NAME_DIALOG_WIDTH)`（`:109`），与存档重命名同一个常量。右上 `✕` 来自 `Dialog::close_button` 默认 `true`。
- **footer 只有两枚按钮**：`group-name-cancel`（Secondary）/ `group-name-ok`（Primary），都 `.small()`，`debug_selector` 同名（`:111-136`）；没有左侧文字槽——「项目「营销分析」」这类信息无处可放。
- **占位符其实由宿主设**：`InputState::new(window, cx).placeholder("分组名")` 在 `request_create_group` / `request_rename_group` 里建输入时给（`group_actions.rs:17-19`、`:54-56`）；对话框自己算出 `placeholder` 后 **`let _ = placeholder;` 丢掉**（`group.rs:67`）——视觉无影响，但把占位符挪进对话框会踩空。
- **闸门只有一条**：`value.trim().is_empty()` → 「分组名不能为空」，转 `warning` 色（`group.rs:64-66`、`:95-105`）。**没有 `Unchanged` 那一档**——这是它与 20 页存档重命名最大的差别；名字没改也能点「保存」，而 `rename_folder` 对「改成当前名」是**幂等返回原行**（`store/folder.rs:107-109`），于是回执照样说「已把分组改名为「X」」。
- **`Enter` 同款关窗缺口**：`on_ok` 恒返回 `true`（`group.rs:137-140`）→ 空名时按 `Enter` 仍然关窗，分组没建成、也没有提示。保存按钮那条被 `.disabled(!can_submit)` 挡住了，键盘这条路没挡（与 `rename.rs:212-215` 同一写法）。
- **三处入口，没有「＋ 新建分组」按钮**：`request_create_group` 只有三个调用点——分组头右键「新建分组…」（`resource_view/list_delegate/group_header.rs:147-149`）、行右键「移动到分组 ›」末项（`list_delegate/menu.rs:241-244`）、详情「移动…」末项（`detail_view/body_sections.rs:237-239`）。重命名入口只有一个：分组头右键「重命名…」。
- **前置拒绝三句**：无项目根 → 「资产库：无法新建分组：还没有打开项目」/「…无法重命名分组…」/「…无法删除分组…」（`group_actions.rs:7`、`:42`、`:176` 各经 `require_project`）；只读项目三条统一「资产库：项目为只读模式，不能改分组」（`:10-13`、`:45-48`、`:179-182`）——分组动作在只读下整类禁止，不像改名那样分成「显示名 / 别名」两句。
- **删除走组件 `AlertDialog`，不是自绘**：`window.open_alert_dialog` + `alert.confirm().title("删除分组「{name}」？").description("组里的存档不会被删，它们会回到「未分组」。")`（`group_actions.rs:189-203`）。因此：宽 **448px**（`Dialog` 默认宽，`vendor/dialog/dialog.rs:223`）、**没有 ✕**（`AlertDialog::new` 自带 `.close_button(false)`，`vendor/alert_dialog.rs:80-84`）、**没有图标**（本处没调 `.icon(…)`）、标题是问句、确认键 `ok_variant(Danger)` = 淡红底实心（`theme/schema.rs:937-947`）。
- **取消按钮显示英文「Cancel」**：只设了 `ok_text("删除")` 与 `show_cancel(true)`，**`cancel_text` 留空**（`group_actions.rs:198-203`）→ 组件库按 `rust_i18n` 默认给「Cancel」。本仓从未把组件库 locale 设为中文，与 15 / 16 页同一条欠债；本处连「取消」两个字都没传。
- **回执分两段**：提交那一刻「正在新建分组「X」…」/「正在重命名分组为「X」…」/「正在删除分组…」（`group_actions.rs:35`、`:78`、`:213`）；工作线程回来后「已新建分组「X」」/「已把分组改名为「X」」/「分组已删除（里面没有存档）」或「分组已删除，N 条存档回到未分组」（`jobs/tag/group.rs:33-57`）——删除的两条按 `delete_folder` 的返回值分开说。
- **删除是事务**：`BEGIN IMMEDIATE` 里软删分组行 + 清成员关联（返回回到未分组的资源数）；成员不跟着删，理由写在注释——「只软删会让关联留在库里，重建同名分组会把旧成员带回来；只清关联又会在列表里留一条空分组」（`store/folder.rs:129-146`）。
- **分组名查重，存档名不查**：`create_folder` / `rename_folder` 都用 `folder_name_taken`（同 `scope` 且 `deleted_at IS NULL`）比一次，撞了报「已经有同名分组「X」」（`store/folder.rs:52-54`、`:110-112`、`:84-96`）。对话框本身不查——用户点「创建」后才在回执里知道。对照 20 页：**两条存档可以同名**，这是两个「改显示名」对话框最实质的口径差异。
- **`scope` 不可编辑**：分组住哪个库决定 `scope`，改名只动 `name`（`store/folder.rs:98` 注释）；`parent_folder_id` 恒 `None`，真传了父分组会被拒（「分组是单层的（没有子分组）——不能指定父分组」，`:46-51`）。

- **提交链路与两条回执**：`enqueue_rename` / `enqueue_set_alias` + `refresh_resources` + 立即回执「资产库：正在把「旧」改名为「新」…」/「资产库：正在更新别名…」（`group_actions.rs:112-125`、`:161-171`）；作业完成后的回执「资产库：已改名为「新」」（**不复述旧名**，`panels/resources.rs:641-642`）/「已把「X」的别名设为「Y」」/「已清除「X」的别名」（`jobs/rename.rs:70-75`）。失败两侧统一「资产库：{action}{reason}」，action 是「重命名」/「编辑别名」。
- **不涨版本**：`rename_resource` / `set_alias` 只 `UPDATE` 一列，**不走 `update_resource`**（后者要 `version + 1` 并写版本快照）（`store/resource/write.rs:58-110`）；`updated_at` 由表上 `trg_ar_updated_at` 触发器维护（`UPDATE OF name` 在其触发列里），代码不重复写。
- **不查重名**：SQL 只有 `UPDATE analytics_resources SET name = ? WHERE id = ? AND deleted_at IS NULL`，`affected = 0` 才报「资源不存在或已删除」（`write.rs:75-84`）。**两条存档可以同名，界面上不提示**——§1 原则 2 只说「显示名与路径分离」，没规定显示名唯一。
- **别名存 NULL 不存空串**：`set_alias` 里 `alias.map(str::trim).filter(|v| !v.is_empty())`（`write.rs:97`），理由写在注释：空串会在界面上变成「有一行空别名」。

### 4.1 归档（M6 自有入口发起）

```mermaid

    participant P as 资产库面板
    participant PD as 草稿挑选对话框
```

> **第二条入口（2026-11-06 接上）**：草稿箱面板的文件行右键也有「归档为存档…」——
> 序列图的后半段完全相同（从 `PD` 往后），只是起点换成 `S 草稿箱行`：
>
> ```
> U->>S: 文件行右键 →「归档为存档…」
> S->>P: 宿主端口 archive_drafts（只递绝对路径）
> P->>PD: 一条 → 直接进 D；多条 → 预勾上的挑选框
> ```
>
> 分工是依赖方向决定的：只有 `analytics_resource → scratchpad`（候选要读草稿目录与
> `file_meta`），所以草稿箱只开端口、不碰归档逻辑。`Ctrl+Shift+A` 仍只落到
> 「从本地文件归档…」（见 §9），草稿行那条**没有快捷键**。

归档确认对话框字段：

| 字段 | 默认 | 说明 |
| --- | --- | --- |
| 显示名 | 文件名（去扩展名） | 可改 |
| 别名 | 空 | 可空（空 = 不设；只影响检索与显示，不动物理文件名） |
| 目标位置 | `resources/<草稿相对路径>` | 不可编辑（保留目录结构，避免同名冲突） |
| 分组 / 标签 | 空 / 空 | 可空；**标签按名找、找不到就建**（同名复用） |
| 来源连接 | 草稿 `file_meta.preferred_connection()`（显式绑定优先，其次 `last_connection_id`） | **自动带出**（归档凭证的关键一环）；存的是连接 **id**，见 §4.1.1 |
| 保留历史内容 | 跟随设置（默认 5 份） | 对话框里可单次覆盖；填 `-1` = 全部保留 |
| 冲突处理 | 询问 | 目标已存在 → 改名 / 取消（不静默覆盖） |

**归档后给撤销条**：底部出现撤销条（沿用 M5 撤销栏；自动消失时长随 M5 一并补）——**撤回 = 删掉 `resources/` 副本 + 删除登记行**（copy 模式；源文件本来就在原处——归档是复制不是搬走，2026-10-13 裁决）；reference 模式只删登记行（本体留原位）。必须给一个立即反悔的窗口。

> **落地现状（2026-09-17，两批，2026-09-18 补两笔）**：对话框已落（crate 内 `dialogs/archive.rs`）——来源 / 目标位置 / 来源连接只读摆出，**显示名 / 别名 / 分组 / 标签 / 保留历史内容都可填**（与原型 §4.1 的字段表一一对应），**目标被占时把"将归档为 resources/x-2.sql"原样摆出**（确认按钮同步改文案）。**撤销栏已落**（面板底部，5 秒窗口；撤回 = 删副本 + 删登记行，见 `service.rs::undo_archive`——copy / reference 两模式已按 2026-10-13 裁决分派；版本 > 1 拒绝，回退请走版本历史）。**草稿来源已接**（面板头 `＋ ▾` → 草稿多选 → 单选展开本对话框）：`source_connection` 与 `promoted_from` 由草稿的 `file_meta` 与相对路径自动带出，**目标位置保目录结构**（`resources/reports/a.sql`）。本地文件那条的这两项仍留空（它没有草稿来路）。**多选那条走默认值批量**：显示名取文件名去扩展名、归档方式固定 copy、分组恒空（没有逐个选分组的输入框），口径与代价见 §4.1.1。

- **选中态由外部持有**：builder 每帧重建，`PickDialogState` 必须建在闭包外（`Rc<RefCell<Vec<bool>>>`，`pick.rs:50-86`）；窗口测试从 `open_draft_pick_dialog_with` 这条缝把状态递进来（`:116-122`）。单测只钉住「全不选 = 不提交」与「顺序跟列表一致」（`:297-318`）。

### 4.3 版本历史对话框

| 区域 | 内容 |
| --- | --- |
| 版本列表 | 版本号 / 归档时间 / 大小 / 指纹前 12 位 / 内容副本是否存在（`缺失` 徽标） |
| 差异 | 相邻版本显示"大小 ±N · 指纹变化"（**不做行级 diff**——文本 diff 归编辑器） |
| 动作 | **选中版本后出现在表格下方的动作栏**（而非每行行内按钮，768px 装不下 7 列）：还原为当前版本（生成新版本，不覆盖历史）/ 取回该版本为草稿 / 删除该版本的内容副本（保留元数据行） |

> **不做"原地回滚"**：存档只追加不修改。回滚在语义上是"用旧内容产生新版本"，与 git `revert` 同构。

> **落地现状（2026-09-17）**：对话框已落（`dialogs/version.rs` + `present::build_version_rows` + 宿主接线）。六列**含当前版本那一行**（写前快照语义下版本表里没有它）；动作栏选中历史行后出场，三个动作都是真执行（还原 = 生成新版本；取回该版本 = 草稿箱里一份“（vN 工作副本）”文件；删副本走 `AlertDialog` 二次确认，副本不进回收站）；动作完成后宿主**再取一次版本并把行换掉**，所以不必关窗重开。**两处有意留白**：版本列表最多 50 行（多的明说“还有 N 个更早的未列出”，不静默截断，也不为它手搓虚拟化）；列里不给“最近 3 条”那种明细。

> **按 `dialogs/version/{mod,open,render}.rs` + `present/versions.rs` 复核（2026-11-07）**：上面三行表与「落地现状」都是设计语气，实现把细节定成了下面这些（原型页已按此重画）。

> - **列序与列名**：六列是 `版本 | 时间 | 大小 | 指纹 | 变化 | 副本`——「变化」在**指纹之后**（原型把`相邻版本差异`放第 4、`指纹前 12 位`放第 5，正好对调）。列宽 `VERSION_COL_VERSION 3.5rem` / `TIME 8.0` / `SIZE 5.0` / `HASH 9.0` / `COPY 5.0`，变化列 `flex_1`；表头是 `header_line()` 的 `px_2 py_1 + border_b(HAIRLINE)`，行是 `ListItem`（`.px_2().selected().on_click()`，`debug_selector("version-row-{v}")`），不是 `table.dt`。
> - **「当前」是版本列里的一段 success 色文字**，追加在 `vN` 后面（不是带框角标）。另外标题就是 `版本历史 · {name}`（无副标题行），而「当前版本 vN」是**内容末尾**再加的一行 muted 小字（`open.rs` 里 `.footer(...)` 之后又 `.child(...)`）——它在动作栏下方、footer 上方，不是标题下。
> - **副本列是纯文本「在位」/「副本缺失」**（后者 danger 色），不是 `存在`/`缺失` 徽标；`has_copy` 对当前版本恒为真（本体在位）。顺带一处欠债：这里与列表徽标、分组计数一样都是纯文本，`rds-design` 要求状态徽标走 `badge::Badge`。
> - **变化列文案由 `version_delta` 生成**：`较 vN 大小不变|大小+{size}|大小-{size} · 指纹相同|指纹已变`，前后两版**都有该字段**才比（快照缺字段就不编），两样都比不出来时给**空串**；最旧一版没有可比的前一版，所以**空着**（不是「—（初始版本）」）。行构造只认 `version - 1` 那一行（`candidates.get(index + 1).filter(...)`），中间缺号时宁可空着。
> - **列表上方一行「共 N 个版本」**（`justify_between` 的左侧），右侧是动作期提示（warning 色，如 `正在还原 v2…`）。**footer 只有一个「关闭」**（Secondary small）；原型那句「共 3 个版本 · 2 份内容副本 · 保留策略「最近 5 份」」不存在——副本份数与保留策略要遍历目录才知道，对话框不做计算。
> - **未选中时动作栏整块不渲染**（`if let Some(row) = state.selected_row()` 才 `child(action_bar(...))`），所以原型 A 的「选中一行历史版本后可对比 / 还原 / 取回 / 删除副本」提示条也不存在。
> - **动作栏四按钮的真实文案与样式**：`与当前版本对比…`（ghost）/ `还原为当前版本（生成 v{N+1}）`（**唯一的非 ghost**，当前行时文案变 `当前版本` 且置灰）/ `取回该版本为草稿`（ghost）/ `删除内容副本`（ghost，不带「该版本的」）。按钮下方一行 `hint()` 小字，按状态四选一：只读「项目处于只读模式：还原 / 取回 / 删副本都是写操作」；当前行「这是当前版本（本体上的内容）：取回请用详情面板的「取回（检出）…」」；无副本「该版本只留了元数据（内容副本已被保留策略裁剪），不能还原或取回」；常态「还原 = 用这一版的内容生成新版本；取回 = 复制一份可写草稿（本体不动）」。
> - **可用性是两条式子**：`can_act = !is_current && has_copy && !busy && !read_only` 管还原 / 取回 / 删副本；`can_diff = !is_current && has_copy && !busy`（**不看 read_only**）管对比。由此两处与原型不同：**副本缺失的行四个动作全灰**（连「删除内容副本」也灰，副本本来就不在了），不是「只留删除副本」；**只读项目下对话框照常打开**、写动作灰、对比仍可点（这也与 §4.2 取回相反——取回在入口就挡回，版本历史是要让人看得到的）。
> - **删副本先过一次 `AlertDialog`**：标题「删除 vN 的内容副本？」，正文「版本记录会保留（列表里仍能看到这一版），但它的内容将无法再还原或取回。副本不入回收站，删除后不可恢复。」；确认后置忙并给提示。还原 / 取回也都会先 `set_busy(true)` + `set_note`（`正在还原 vN…` / `正在取回 vN…`），**对比不置忙、不开回执**（它只打开 `version_diff` 查看器）。动作执行完宿主 `set_rows` 换行、**不关窗**；选中项不在新行里才清空，否则保持选中。
> - **列表高度 `VERSION_LIST_MAX_HEIGHT 20.0rem` 内滚动**（`max_h + overflow_y_scrollbar`）；超过 `MAX_VERSION_ROWS = 50` 时末尾补一句「还有 N 个更早的版本未列出（一次最多列 50 个）」。行点击只写 `set_selected(Some(version))`——**再点同一行不会取消选中**。
> - 原型常驻的那段说明（「不做原地回滚：还原 = 用旧内容生成新版本（与 git revert 同构）…内容副本按「最近 5 份」保留」）在实现里**不常驻**，只剩动作栏下方那一行 hint；「不做原地回滚」这条语义本身是对的，只是搬进了 hint 与提示语。

> **版本对比对话框（§4.3 扩展）按 `dialogs/version_diff.rs` + `jobs/version.rs` 复核**（2026-11-07，14 页）：
> - **尺寸是两个常量**：`DIFF_DIALOG_WIDTH 64.0`（`font_size * 64` = **1024px**）、`DIFF_LIST_MAX_HEIGHT 28.0`（**448px**）。标题 `{name} · v{old} → v{new}`，**没有副标题**（原型写的「只读 · 文本 diff」不存在）；标题里的 `old → new` 是「被比的那一版 → 打开时的当前版本」。
> - **顶栏是一行 + 两个按钮**：左侧 `v{old} → v{current} 的差异（只读）`（`text_xs` + muted），右侧 `h_flex().gap_1()` 里两个 **ghost small `Button`**（`diff-mode-unified` / `diff-mode-split`，`.toggled(...)` 表示当前形态）——**不是分段控件**（原型 `.mode-sw` 那种）。点击只做 `state.set_mode(DiffMode::Unified|Split)` + `window.refresh()`，**不重算 patch**。
> - **主体是组件不是自绘表格**：`Diff::new(&state).line_number(true).syntax_highlight(true).hover_highlight(DiffHoverHighlight::Line).max_h(rems(28.0))`。由此三处与原型不同：① 行号是**旧 / 新两条 gutter**（删行只有左号、增行只有右号），不是共用一列；② 有**文件头**（`document.path()`，本仓即 `dau_report.sql@3`，右侧 `+N −M` 统计，左侧 `collapse-file` 折叠箭头可整块收起）与 **`@@` hunk 行**；③ `soft_wrap` 默认 `false` → **不折行、横向滚动**（组件自带 `ScrollableMask`），原型那句「超长行一律省略号 + tooltip」不成立。
> - **footer 只有一个按钮**（`diff-close`「关闭」，Secondary small）；原型的「2 处变更 · 8 行上下文」不存在——增删统计在文件头。也没有表单、没有确认动作：这个对话框**只读**，不写库、不产生版本。
> - **入口只有一处**：版本历史动作栏的「与当前版本对比…」（`Dialogs` 里 `VersionAction::Diff` 分支只开这个查看器）。原型标的「第二入口 = 详情面板版本区『查看全部…』」**是假的**：那个按钮走 `host.request_version_history` → `enqueue_versions`，**只开版本历史对话框**，不直接开 diff（`detail_view` 里 `grep 对比|version_diff|Diff` 零命中）。
> - **只读项目也能看**：宿主 `request_version_action` **先判 Diff** → `enqueue_version_diff` + `ensure_resources_pump` 后直接 `return`，注释写明「只读项目也能看差异」；只有其余三个动作才走 `if read_only { finish_version_action("项目为只读模式，不能改版本") }`。这与 §4.2 取回相反（取回在入口就挡回），口径是「版本历史 / 对比是要让人看得到的」。
> - **`DiffState` 必须在 `open_dialog` 之前建好**：builder 是 `Fn`（每帧调），在 builder 里新建 state 会每帧丢。`parse_display_patch` 只在 `DiffFile::parse` 成功**且非空**时返回 `Some`；`open_version_diff_dialog` 收到 `None` 时先 `on_close(cx)` 再 `return`——**连窗都不开**。
> - **失败不走版本动作回执**：成功时 `shared.version_diff_pending.pending = Some(rows)` + `notify_host` + `cx.notify()`；失败时直接 `shared.say_error(format!("资产库：无法对比版本：{err}"))`（面板通知条）。`VersionAction::Diff` 在 `run_version_action` 里是 `unreachable!`——diff 不走后台动作队列，由 `enqueue_version_diff` 单走一条通道。
> - **两版文本怎么取**：新侧 `read_resource_text`（按本体路径读），旧侧 `payload().version_copy_file(...)`（读那一版的内容副本）。旧副本缺失的文案是「该版本的内容副本不在（已被保留策略裁剪），无法对比」；**两侧都超限才挡**（`DIFF_MAX_TEXT_BYTES = 512 KB`，单侧超也挡那侧）。
> - **四种「打不开」的文案都在 `jobs/version.rs`**：无 `file_rel_path`「该存档没有本体路径（可能是分析表档），无法对比」/ 本体不在位「本体不在位（可能是缺失存档），无法对比」/ 非 UTF-8「该文件不是文本（可能是二进制），无法对比」/ 过大 `DIFF_TOO_LARGE`「文件过大，请用编辑器查看差异」。**都不弹窗**，全走面板通知条。
> - **patch 由 `unified_patch` 生成**：`similar::TextDiff` + `.context_radius(3)`（前后 3 行上下文），头两行 `a/{name}@{old}` / `b/{name}@{new}`——所以文件头显示的 `@3` 是**版本号**不是行号。
> - **三条单测钉住边界**（`dialogs/version_diff.rs`）：`real_patch_yields_one_file`（一个 patch 只出一个文件、`files[0].path() == "dau.sql@3"`、`additions() == 1`）、`empty_patch_opens_nothing`、`garbage_patch_opens_nothing`（后两条断言「不弹窗」）。
> - 原型 `.diffview` / `.drow` / `.dno` / `.dc` / `.difftool` / `.mode-sw` 是照「共用一列行号 + 分段控件 + 自绘行」画的旧账，现页已改用内联样式自绘；这六条 CSS 目前**无任何页面引用**（要不要从 `proto.css` 删掉待定，删会动「320 个 css_class」的计数口径）。

> - **只读项目对话框照常打开**：三个写动作全灰（`can_write = false`），宿主 `request_trash_action` 另挡一道「项目为只读模式，不能改回收站」，无 root 时「还没有打开项目」。与 §4.2 取回相反（取回在入口就挡回）。
> - **两个来源归并**：`load_trash` 把 `PayloadStore::trash().list()` 的实体条目（走文件系统，不碰项目库）与 `service.deleted_reference_archives()` 的软删 reference 登记行（没有本体可搬）按删除时间**双指针归并**成一份倒序清单；项目库读不到时只 `tracing::warn`，**不弄砸实体清单**（reference 条目不显示）。`TrashRow` 九个字段：`trash_id` / `name` / `original_label` / `kind_label` / `time_label` / `size_label` / `payload_mode` / `resource_id` / `has_payload`。
> - **落地路径是目录不是单文件**：`crates/analytics_resource/src/dialogs/trash/{mod,open,render,tests}.rs`；旧稿写的 `dialogs/trash.rs` 是假的（本段已把上面「落地现状」段的同一处一并改成目录口径）。

#### 5.1 空态与异常（19 页）实现复核（2026-11-07）

> 逐条对回 `resource_view/panel_render/`、`detail_view/` 与 `filter/`；与 §5 表格冲突处以本节为准。

- **分流只有两条判据**：`view_rows.is_empty()` 与 `filter.is_empty()`（= 搜索词 / 种类 / 标签 / 只看异常四维全空，`crates/analytics_resource/src/filter/mod.rs:146-151`）。有行 → `List`；没行且条件空 → 骨架（取数期）或空库；没行但条件非空 → 无匹配（`resource_view/panel_render/mod.rs:47-62`）。**实例（全局 / 项目）不在这两条判据里**，是面板级 `InstanceFilter`。
- **空库两枚按钮，都受只读门禁**：标题「还没有任何存档」、说明「把草稿箱里值得留存的文件归档进来，它就变成只读、带版本、可追溯的存档」（`panel_render/empty.rs:55-65`）；按钮「从草稿箱归档…」（`primary`，`id=archive-for-empty`）与「从本地文件归档…」（`secondary`），两者都 `.disabled(read_only)`（`empty.rs:76-101`）。§5 表格原写的第二枚「了解资产库能做什么」与建议行「草稿箱里有 3 个文件值得归档」都不存在——`EmptyContent` 只有这两个子元素。
- **全局空一枚按钮都没有**：`is_global` 时只拼 `EmptyHeader`、不拼 `EmptyContent`（`empty.rs:73-74`），并且文案换成「全局实例还没有存档」+「升级到全局后会出现在这里；全局实例不直接归档，跨项目分发都从这里选」。旧稿画的「了解全局共享规则」按钮是凭空的。
- **无匹配的副文案只吃搜索词**：`filter::no_match_hint(query)` 两档——无词「去掉几个筛选条件，或清空筛选」，有词「换个关键词，或改搜这些字段：显示名 / 别名 / 标签 / 来源表 / 尾部信息」（`filter/mod.rs:239-245`）。有词那档反给 `SEARCH_FIELDS`（`mod.rs:233`）才知道能搜什么；**不列举当前条件、不数「几个条件叠加」**。按钮是「清空筛选」（`ghost`，`empty.rs:120-128`）。
- **加载骨架只有灰条，没有文字**：三条 `Skeleton`，宽度比 `0.75 / 0.55 / 0.65`、高 `ui::ROW_HEIGHT`（24px）、`gap_2` + `p_2`，挂 `debug_selector = archive-loading` 供窗口测试断言「取数期间不摆空态」（`empty.rs:28-47`）。「加载中…」只做状态行前缀且**不抹掉计数**（`view_model/row.rs:100-108`），全局实例换成「加载中… · 全局 N 项」（`panel_render/banners.rs:84-95`）。
- **列表区一次性提示条已做（§5「未做」清单里那条已过期）**：`render_index_issue_banner` 只在**项目实例**、`counts.has_issues()`、且本会话没被关过时出现（`panel_render/banners.rs:121-174`）；文案「发现本体缺失 N 项、内容已变 M 项，可在状态行「修复…」处理。」，`×` 关掉后靠 `announced_index_issue` 内存标记本会话不再出现；全局实例直接返回 `None`。
- **顶部条整块不可点**：要处理走底部状态行的「修复…」（`banners.rs:112-119`）。旧稿「点横幅 = 打开索引修复对话框」不成立——那枚钮在状态行，不在横幅上。
- **详情横幅共五档**（`detail_view/rows.rs:96-120`）：本体缺失 / 内容已变（分析表用 `analysis::STRUCTURE_CHANGED_NOTE`，与文件型字节级分开说）/ `TableRef` 常态提示 / 引用型常态提示；都是 warn 描边 + warn 文字的纯文本条，**没有按钮**（`detail_view/banners.rs:14-26`）。文案指向**索引修复**，不是旧稿写的「从回收站还原」——回收站对本体缺失行是拒绝的（`detail_view/actions.rs:89`、`service/trash.rs:15`）。
- **引用失效条是独立一条**：文案「源已变更，快照失效：当前源文件与归档时的指纹不一致。」+「接受当前内容」「从历史还原」两枚 `ghost xsmall`；槽位由宿主按 `resource_id` 维护，不进索引统计（`detail_view/banners.rs:28-87`）。
- **另两条容易漏的**：`render_notice` 是一条纯文本条，同一字段按 `read_only` 决定 warning / info（`panel_render/banners.rs:12-17`）；撤销栏「已归档「X」+ 撤销」高度压在 `ROW_HEIGHT`、固定在状态行上方（`banners.rs:31-74`）。
- **状态行原文**：`N 项 · 已归档 N`，再按非零追「分析表 / 引用 / 缺失 / 索引异常」（`view_model/row.rs:82-98`）；异常时整行转 warning 色并给「修复…」。
- **欠债两条**：① 详情横幅纯文本、没有「去修复」入口，且与面板条文案不一致（面板条说「可在状态行「修复…」处理」，详情条说「可用索引修复还原或删除记录」）；② 加载期被筛选挡住——`filter.is_empty()` 才给骨架，条件非空时取数期直接摆「没有匹配的存档」，队列还没回来就先宣布没匹配。

## 6. 主题映射（token → 视觉）

> 全部使用既有角色，**不新增产品语义 token**（`danger` / `success` / `warning` / `info` 已足够表达三档强度）。

| 区域 / 元素 | 角色 |
| --- | --- |
| 面板背景 / 分隔 | `background` / `border` |
| 面板头 | 标题 `foreground`；动作按钮 `secondary` + hover `secondary_hover` |
| 工具栏输入框 | 底 `background`，边 `input_border`，聚焦 `ring` |
| 列表行 | `list` / hover `list_hover` / 选中 `list_active` + `list_active_border` |
| 分组头 | 色条 `primary`（**与 M4 分组头同角色**；它与 `list_active_border` 在 `rds-theme.json` 里明暗同值，故 V2 改角色是零视觉变化。**不用 `sidebar_accent`**：该角色在浅色下与面板底几乎同色）；展开指示 `muted_foreground`；文字 `muted_foreground` |
| **复现强度徽标** | `已归档` = `success`；`分析表` = `info`；`引用` = `warning`（`TableRef` 已划掉，徽标档位仅对旧行读取兼容） |
| 缺失 / 错误 | `danger`（点 / 纹理 / 文字，不整行染色） |
| 只读提示条 | `warning` 描边（与编辑器只读条一致） |
| 内容已变 | `warning` 徽标 |
| 状态行 | `muted_foreground`；异常段 `warning` / `danger` |
| 空态图标 | `muted_foreground` |

**kind 图标（形状区分，不靠颜色）**：`File` = 文档形；`Analysis` = 表格/数据库形；`TableRef` = 链接/箭头形。图标一律用 `muted_foreground`，**不按 kind 各自带色**——这样**复现强度徽标是行内唯一的色块**（视觉通道预算：一行只允许一个颜色信号）。图标从 `assets/icons` 既有资产选取（`gpui-kit-assets` 全量目录），缺图标时按资产路径补。

**色值基准（硬约束）**：

1. 实现一律取 `cx.theme().colors.*`，**禁止硬编码**；注意 `*.background` / `*.foreground` 是**成对角色**（填充色 + 其上文字色），不是“浅底深字”的弱色对。
2. 视觉稿（原型 HTML）的取值口径沿用本仓既有原型稿的语义前景配对（同 `../scratchpad/scratchpad-prototype-design.md` §6.1）：浅色 `success` `#16A34A` / `warning` `#B45309` / `info` `#2563EB` / `danger` `#DC2626`；暗色 `#89D185` / `#CCA700` / `#3794FF` / `#F14C4C`。
3. 行内徽标与提示条的**底色从语义色派生**（`color-mix` 10–14% 叠底），不硬编码第三组 hex；若将来要改成“实底徽标”，则用 `*.background` + `*.foreground` 成对填充。

> 已知欠债：旧原型稿里出现的 `#0F2A4A` / `#3A3105` / `#4A1A1A` 等语义底色**不在主题资产中**，属自创值——以本文件的口径为准，旧稿待顺手校正。

**② reference 型打开时的指纹校验反馈**：

- 双击 / 右键「打开（只读）」：先 `resolve_source` 定位源文件 → 比对登记指纹（`PayloadStore` 读源并计算）。

**③ reference 型删除入口**：

- 行右键「移入回收站」对 reference 型可用（与 copy 同一判据）。
- 二次确认文案按模式区分：copy =「将删除 `resources/` 副本与登记行」；reference =「本体留原位，只删除登记行」。
- 回收站条目还原语义：copy = 从回收站还原副本；reference = 还原登记行（本体从未移动）。「永久删除」对 reference 型仅删登记行，`AlertDialog` 文案同步说明。

**详情面板差异（reference 型）**：基本信息区「物理存储路径」显示源绝对路径；「大小」显示源文件大小（读不到显示 `—`）；只读提示条文案：「引用型：本体在源位置，源变更后快照失效」（区别于 copy 的「归档后不可写，需取回编辑」）。

#### 12.2.1 A2 data 视图（analysis 档）规格

> 2026-10-13 裁决 16：「洞察归档 = 一资产两视图」已拍板方向，**本期做 / 不做待用户决策**；本节给出完整交互规格，决策通过后按此实现。核心命题对齐架构文档：「分析资源 = 结果集的变体（配方 + 小快照 + 元数据），可复现、不占盘；复现依赖源版本还在」。

**归档入口（档位选择）**：洞察集合卡「归档」当前是**一键入库、没有对话框**（T20 实际装配，见 §12.2.2）；若 data 档通过决策，需先补一个可选择的入口（对话框分区或行内菜单），再按下列两档落：
- **报告（file 档，T20 现状）**：结论文本渲染快照，走 File 档 copy（`resources/insight/`）。
- **数据（analysis 档）**：快照 = 画像结构化数据 + 配方；登记为 `Analysis` 档（`ArchiveKind::Analysis`），落盘路径同 `resources/insight/`。

**data 档快照内容**（与 `InsightSnapshotMeta` / `TableProfile` 字段一致，单一来源）：
- 表级画像：列名 / 类型 / 可空 / 主键 / 行数 / 列数 / 逐列统计（缺失率 / 唯一率，来自 `compute_table_column_summary`）；
- 配方：取样查询 SQL（`SampleSource.sql`，不带 LIMIT 的全量语义由 `full: bool` 决定）+ 规则集引用（洞察规则清单，含 `category` 与版本）；
- 元数据：`generated_at` 时间戳、`binding.source_table` = 表名（与 file 档同）。

**打开（data 档）**：双击 / 右键「打开（只读）」→ `Analysis` 档语义：
- 源可访问 → 按配方重跑取样查询 → 结果集进中间页二次分析（**只能 DuckDB 分析**，`create_analysis_temp_table` 路径）；
- 源不可访问（purge 后）→ 提示「配方作废，源版本已删」，配方区灰显，血缘字段给出「源已删」可读性（架构核心命题）；
- 指纹口径：Analysis 档指纹 = sha256(定义 ␀ 列结构摘要)，**行数不进指纹**（架构裁决）——data 档同口径。

**版本链**：data 档与 file 档**共享版本链**（一资产两视图）：同一次洞察归档产生 data 快照与报告快照，登记同一 `resource_id`，各视图对应独立版本号；`keep_versions` 裁剪时两视图按各自版本链独立保留。

**与 T20 的关系**：T20 已实现的是「报告 file 档」路径（`export_table_snapshot` → `enqueue_archive`）。data 档若本期做，复用同一入口，新增 `ArchiveKind::Analysis` 分支与配方导出；若不做，文档保持「当前仅 file 档」标注，决策后更新本节状态行。

> - **升级侧版本接续是真的，分发侧不接续**（一处口径不一致，只记不改）：`register_global` 取 `MAX(version) WHERE name = ?1 AND scope = 'global'`，**不带 `deleted_at IS NULL`**——覆盖时旧行已软删但仍在表里，所以新版本 = 旧版本 + 1（v4 → v5）；而分发侧 `distribute_overwrite` 先软删项目旧登记，`register_project_table` 的 `MAX(version)` **带 `deleted_at IS NULL`**（`global/register.rs:39`）→ 取不到 → 新登记从 **v1** 重新开始。本节 §13.6 那句「分发版本号接续全局链」也不成立：`next_version` 只查项目侧 `scope='project'`，`global_version` 仅作为 `distributed_from` 快照里的一个字段。
> - **单测就一条**：`rename_gate_blocks_blank_and_unchanged`（空名 → `Blocked("显示名不能为空")`；原名 / 带空格的原名 → `Unchanged`；新名 → `Ready`）。

#### 13.3.1 升级到全局（23 页）实现复核（2026-11-07）

> 逐条对回 `resource_host/detail_actions.rs::request_promote_to_global`、`resource_host/mod.rs`（两张白名单）、`global/promote.rs`、`global/register.rs::register_global`、`jobs/global.rs::run_promote` 与 `resource_view/list_delegate/{menu.rs,mod.rs}`。

- **入口只有一处**：项目行右键「升级到全局…」（`menu.rs:103-115`）。判据 `.disabled(!can_open || multi_count > 1 || read_only)`；`can_open = status != Missing && payload_rel_path.is_some()`（`list_delegate/mod.rs:203-208`）。详情面板**没有**升级按钮——全仓只有 `menu.rs:111` 一处调用 `request_promote_to_global`。
- **分析表型存档在菜单上就是灰的**：`can_open` 含 `payload_rel_path.is_some()`，而分析表型（kind = analysis）的本体在项目 `analytics.duckdb`、没有相对路径。所以宿主那句「资产库：分析表型存档的升级随 M8 后续批次接入」（`detail_actions.rs:158-161`）**在 UI 上不可达**——它是一道防御分支，不是用户会看到的话术。
- **形态判定是两张正向白名单，不是一个「其余」兜底**：数据文件 8 个 `csv | tsv | txt | parquet | xlsx | xls | json | ndjson`（`is_data_file_ext`，`mod.rs:369-377`）；文本脚本 12 个 `sql | py | r | md | yaml | yml | toml | js | ts | sh | ps1 | ipynb`（`is_text_script_ext`，`mod.rs:384-392`）。两表之外（png / jpg / zip / docx、或没有扩展名）**在入队前就回执**，一句话点名扩展名并给两条出路（另存 csv / 走分发或共享目录，`detail_actions.rs:174-189`）。这处是修 `Script` 分支 `fs::read_to_string` 撞 UTF-8 那批补的（原先把 `stream did not contain valid UTF-8` 技术原文丢给用户）。
- **前置拒绝一共三句**：无项目根「无法升级：还没有打开项目」、只读项目「项目为只读模式，不能升级」、本体文件不存在「资产库：本体文件不存在（{rel}），无法升级」（`detail_actions.rs:152-166`）。
- **数据文件 = 真表**：`CREATE TABLE <name> AS SELECT * FROM <file_read_expr>`（`promote.rs:69-78`），行数 / 列数由建完的表**真量**（`table_stats`）后写进登记。
- **脚本 = 单行内容表**：`(filename, content, content_hash)`，正文整段 `INSERT`（`promote.rs:89-112`）；**行数 1 / 列数 3 是写死的常量**（`:112`），不是量出来的——内容表的统计口径与数据表不同。
- **全局登记的落值**（`register_global`，`register.rs:219-250` 的 INSERT 实参）：`scope = 'global'`、`kind = 'analysis'`（**一律按分析表登记，不继承项目侧的 file / analysis 档**）、`readonly = 1`（全局侧只读是登记行自带的，不靠界面约定）、`payload_mode = 'copy'`、`file_rel_path = req.rel_path`、`definition_sql` 有值（数据文件是建表 SQL、脚本是一句中文描述）、`source_path` = 项目侧的**绝对路径**（换项目或换机器就没有意义）；`alias` / `created_by` / `promoted_from` / `parent_version_id` / `parent_resource_id` / `source_connection_id` / `source_table` / `source_query` **全部 NULL**——**没有「谁升过来的」这条线**。
- **版本号 = `MAX(version) + 1`，且查询不带 `deleted_at IS NULL`**（`register.rs:192-198`）：覆盖时旧行已被软删但仍在表里，所以版本号能接续（v4 → v5）；新名字第一次升级从 v1 起。
- **「覆盖」不是覆盖同一行**：`drop_global_table` + `UPDATE … SET deleted_at`（软删旧登记，**不硬删**）+ 再走一遍 `promote`（`promote.rs:125-146`）→ 新行是新的 `arg_<uuid>`，有自己的版本快照。于是「版本接续」只是**数字**接续：版本历史按 `resource_id` 查，新行只看得到自己那条 v5，看不到被软删的 v4（那是另一个 id）。§13.2 说的「一条记录挂多版本」在升级路径上不成立。
- **覆盖没有跨库事务**（`promote.rs:130-142`）：`drop_global_table` 走 DuckDB、软删登记走全局 SQLite，两次独立 execute，中间失败也没有回滚——留下的正是 `promote` 里那两种脏状态（表没了登记还在）。而冲突框对「表在登记不在 / 登记在表不在 / 都在」只报同一个 `Conflict { name }`，用户分不出「有没有旧表可删」（扩展字段才能带上版本号与来源项目，与 17 页那条同源）。
- **两条回执**：入队时「资产库：正在升级到全局…」（`detail_actions.rs:203`），覆盖分支换「正在覆盖升级到全局…」（`panels/resources.rs:214`）；完成后统一「资产库：已升级「X」v{n} 到全局实例（跨项目可分发）」（`:659-661`）——**首次升级与覆盖共用这一句**，回执不区分两者。
- **没有前置确认框是规格没要求**：§13.3 只写「表名默认取显示名，冲突时询问改名」，没要求入队前先确认。原型 23 页那块 544px 的「升级确认框」是**提案**，代码里没有 `PROMOTE_*` 宽度常量、也没有对应对话框文件；真要加，得先定「升级前能不能改名」（不改名，改名入口就只能待在冲突处置里）。
- **注释与实现的陈旧**：`jobs/global.rs:35-36` 写「其余（sql/py/md 等）→ 脚本内容表」（实际两表之外的二进制被拒，不是进内容表）；`promote.rs:121-124` 把冲突询问挂成「§13.2」（在 §13.3），且「成为新版本（版本号接续旧链）」容易被读成同一行。另 `promote.rs:129` 留着一条 `tracing::info!("【探针】升级到全局 promote_overwrite 进入（覆盖）")`，属调试残留。

### 13.4 与既有概念的关系

- **`promoted_from`（草稿 → 归档）与 `scope`（项目 → 全局）是两层升级，不混用**：前者追来源草稿相对路径（`model.rs:105`），后者记实例归属。
- **tag 先例（2026-11-07 按源码修正）**：标签**定义**在全局库跨项目共享（§12.3），但**资源 ↔ 标签的关联仍在项目库**；升级到全局的行登记在全局库，详情面板对 `scope = Global` 的行**不渲染标签区**（`detail_view/body_sections.rs` 的 `detail.scope != RowScope::Global` 条件）——所以全局行没有「带着升级前的标签」这回事，要打标请在分发回项目之后打。
- **洞察归档（T20）**：快照进 `resources/insight/`、`scope=project`；若需全局共享，走本节升级。
- 连接层路由（`G_` / `P_` / `GP_` 前缀，`workspace_loader.rs:77`）已区分实例，M6 升级写入走 `G_` 连接即可，无需新增连接体系。

### 13.5 脚本文件（不可映射）的升级处理

> `file_reader_function` 对 `.sql` / `.py` / `.md` 等脚本返回 `None`（`file_reader.rs:50` 测试明证）——没有读取函数，不能按 §13.3「映射出表」路径处理。**2026-10-22 用户定稿：方案 A**。

- **方案 A（定稿）**：脚本以**内容表**形态进全局 DuckDB——`read_text` 语义（单列 `content` + 行元数据：resource_id / name / version / 指纹 / 原始相对路径），版本信息随行。分发到项目（§13.6）时**重建为文件**（`resources/<path>`），项目 B 拿到的是可编辑脚本。理由：落点统一在全局 DuckDB（符合「表 + 版本信息到全局」）；脚本是文本，`VARCHAR` 无损；分发可逆（表 → 文件）。
- **方案 B（不采用）**：全局系统目录新增 `{system}/resources/` 存脚本副本——语义与项目侧文件型同构，但全局多一个存储形态，与"落点在 DuckDB"不一致。
- **二进制 / 不可读文件**：**2026-11-07 已落前置拒绝**——`resource_host::{is_data_file_ext, is_text_script_ext}` 两张正向白名单之外的扩展名（png / zip / docx 等）在**入队前**回执「全局库只收能读成表的数据文件（csv / tsv / parquet / xlsx / json 等）或文本脚本（sql / py / md 等）」，不再以 `stream did not contain valid UTF-8` 的技术原文结束。

### 13.6 全局 → 项目（分发）与跨项目唯一法定路径

- **入口**：全局实例行（`scope=global`）右键「分发到本项目…」**与详情面板同一颗按钮**（`archive-detail-distribute`，走同一条 `request_distribute_from_global`，回执与冲突框一致；原型 `08` 页按实现画出这颗按钮与两态说明）：从全局 DuckDB 读表 → 写入当前项目库（`COPY … TO '*.parquet' (FORMAT PARQUET)` 中转 + `CREATE TABLE AS SELECT * FROM read_parquet(…)`）+ 登记 + 版本链分支（分发版本号按**项目侧**重排：`register_project_table` 取项目侧 `MAX(version)+1`，`global_version` 只写进 `distributed_from` 快照——**不是**接续全局链，见 §13.3 末复核块里那条不一致）；脚本内容表 → 重建为项目 `resources/<path>` 文件。冲突（项目已有同名）→ 询问（覆盖 / 改名 / 取消）。**同样没有前置确认框**，点了即入队。
- **唯一法定路径（架构原则，2026-10-22 用户定）**：**项目 ↔ 项目禁止直传**。跨项目共享的唯一路径 = `项目 A → 全局 → 项目 B`：全局是唯一交换中枢，项目之间互不可见、互不读写（隔离语义：每个项目只看得到自己的库 + 全局库，看不到别的项目库）。任何"从项目 A 直接复制到项目 B"的入口都不提供。
- 全局行只读：分发不删除全局行（全局是长期共享层，`keep_versions` 裁剪由版本规则负责）。
