速览页（权威口径见架构与开发方案）
归档 · 取回 · 版本 · 组织 · 检索

把「这次结论是怎么来的」
连同文件一起冻结下来

资产库不是文件管理器，而是分析存档：每一次归档都留下三件套——来源、代码、内容指纹。 本体一旦归档即只读，要改就「取回」一份工作副本；改完再归档，只有内容真的变了才产生新版本。

草稿箱回答「我正在干什么」，资产库回答「我留下了什么、它当时长什么样」。
3 种存档类型（文件 / 分析表 / 引用）
sha256内容指纹驱动版本
5 秒归档撤销窗口
三重只读守卫
125模块单测全绿
零渲染期 I/O
Why

它替用户挡住的三件事

🗂

「哪一版才是当时那份？」

文件改到第 8 版，报告早就发出去了，却说不清当时用的是哪份、和现在差在哪。

做法：归档案等于当时的字节快照 + 指纹；历史版本可按策略保留，还原永远生成新版本，不覆盖历史。
🔎

「这个结论是用什么数据算的？」

表格躺在某处，SQL 在聊天记录里，连接早就改了名——复盘时全靠回忆。

做法：归档凭证三件套随存档一起留：来源连接 / 来源草稿路径 / 来源表 + 定义 SQL + 内容指纹。
🔒

「借出去改乱了原件。」

把归档文件直接打开编辑，指纹失效、版本失去意义，谁也说不清原件长什么样。

做法：只读是常态。修改走「取回（检出）」——复制一份工作副本到草稿箱，本体永远不动。
Flow

核心闭环：归档 → 取回 → 再归档

与 git「签出 → 改 → 提交」同构

下面这条链路是一期能力的主体；左侧入口（草稿箱 / 本地文件）与右侧出口（回收站）都可撤回。

01 · 发起

从草稿箱或本地文件

面板头 ＋ ▾ 两个入口；草稿来源会自动带出连接与出处。

填写项：显示名 · 别名 · 分组 · 标签 · 保留份数
→
02 · 归档

本体搬进 resources/ 并只读

先算指纹、再搬文件、最后写索引；索引失败会把本体移回原处。

登记 v1 · 凭证三件套 · 5 秒内可撤销
→
03 · 取回

复制一份可写工作副本

工作副本落在草稿箱，本体保持只读；同名自动避让，不覆盖。

本体不动
→
04 · 再归档

指纹变了才 +1 版本

旧内容留成历史副本；指纹没变则幂等返回，不产生假版本。

版本 = 内容，不是「改过名」
撤销归档：本体移回 + 删登记行（5 秒窗口） 历史版本可「还原」或「取回为草稿」 版本行永久保留，内容副本按 keepVersions（默认 5 份，可设全留 / 只留元数据） 不用了：移入项目级回收站 → 可还原 / 永久删除
Features

七个特点

📌

版本由内容说了算

版本号只跟 content_hash 走：改显示名、打标签、归组都不涨版本。

为什么：否则版本化的是「改过名字」而不是「内容」，历史就没有证据价值。
🧾

自带凭证

来源连接 / 来源草稿路径 / 来源表 + 定义 SQL + 内容指纹，随存档一起留。

为什么：复盘的第一个问题是「它从哪来」，凭证缺一项就得靠回忆。
🔐

只读三重守卫

应用层拒绝写入 + 编辑器以只读打开 + 文件系统只读属性（辅助）。

为什么：单靠文件属性在 Windows / 网络盘并不可靠，硬约束必须留在应用层。
🏷

标签为主，分组为辅

标签多值、跨类型通用，可改名 / 删除（删标签不动存档）；分组是单层的，折叠状态会被记住。

为什么：旧版的多级文件夹树从没做完（无改名 / 删除 / 移动），投入产出比差。
🧭

检索与排序

搜索 + 类型 / 标签 / 只看需处理筛选；五个排序键，缺值的行总是排在最后。

为什么：排序比的是原始字节数与时间戳，不是格式化后的 1.2 KB。
🧰

坏了自己能修

索引修复覆盖三类差异：有文件无记录 / 有记录无本体 / 指纹不匹配——全部人工确认后执行。

为什么：静默导入或删除会让「存档」变成用户没同意过的东西。
♻️

回收站是项目级的

与草稿箱共用一套回收站，按来源隔离：只列、只清自己名下的条目。

为什么：共用一处仓库不等于可以替对方清空。
Architecture

分层与真相源

文件系统是本体权威，登记表只是可重建的索引
上游 · M5

草稿箱 / 本地文件

归档的发起方。M6 只收「路径 + 元数据」，不认识草稿箱的内部结构。

依赖方向：scratchpad → analytics_resource（单向，M6 不反向依赖 M5）
宿主 · 工作台

面板装配 · 端口实现 · 后台作业 · 设置读写

取数、搬文件、算指纹都在单工作线程上跑，结果回填给面板；渲染期零 I/O。

workbench：面板挂载 + 宿主端口 + 作业线程（结果槽）+ SettingsService 唯一读写路径
模块 · M6

编排 · 本体 · 索引 · 视图

服务层编排五条动作链；本体层管文件守卫与指纹；索引层管登记、版本、标签、分组；视图层只读快照。

service（编排 + 事件）· payload（守卫 / move / sha256 / 副本裁剪）· store（登记 / 版本 / 组织）· indexer（修复）
磁盘

本体 + 索引 + 回收站

本体可视、只读、可被编辑器打开；索引删了也能从本体重建。

{项目}/resources/ ← 本体（权威）　{项目}/.RSmeta/project.db ← 索引　{项目}/.RSmeta/trash/ ← 回收站

数据链路： 面板（发起）→ 服务（编排）→ 本体层（resources/）+ 索引层（project.db）； 删除走项目级回收站。没有 HTTP / IPC 层，全部在本进程内完成。

Rules

写进代码的硬约束

🧱

本体权威，索引可重建

文件系统有什么就是有什么；登记表坏了可以重建，本体不可重建。

🚚

先本体、后索引

顺序固定：move 本体 → 写索引；索引失败回滚本体，绝不留半成品。

🖥

渲染期零 I/O

取数、扫描、搬文件都在后台线程；面板只读自己持有的快照。

↔️

依赖只向下

模块不反向依赖上游与宿主；设置项由宿主读好后作为参数传入。

🎨

零裸值

颜色一律走主题 token，尺寸常量单一来源——深色主题与缩放不靠猜。

🔕

不静默

失败要么拒绝、要么写进回执：附属项（标签 / 分组）没落上也会说明。
