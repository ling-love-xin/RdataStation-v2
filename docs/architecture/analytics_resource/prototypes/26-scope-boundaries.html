E规格没定的两处【待确认】——两路的代价摆在这里，① 的拒绝回执已落
① 纯文件档 现状 升级入口只判了「是不是数据文件」，其余一律走「脚本内容表」的 read_to_string；二进制因此撞 UTF-8，中文界面里冒出一行 stream did not contain valid UTF-8。2026-11-07 已落：补一张文本脚本白名单（sql / py / md / yaml / ipynb…），两张白名单都不收的（png / zip / docx / 无扩展名）在入队前回执，原话是「png 这类文件不能升级到全局——全局库只收能读成表的数据文件（csv / tsv / parquet / xlsx / json 等）或文本脚本（sql / py / md 等）。内容是数据的话，另存为 csv 再升级；纯二进制文件请留在项目里，用「分发」或共享目录传。」
注意：这只是把失败说清楚，没有回答「要不要支持」。 路径 A 明确拒绝（当前语义，已落）：全局库只收「能读成表的数据」与「纯文本脚本」，二进制留项目侧。代价 0。另一面是：二进制从此没有跨项目路径——分发是全局 → 项目，它进不了全局，也就分不回来；跨项目传 png / docx 只剩共享目录。 路径 B 给全局库加文件承载（全局侧存 blob 路径 + 全局版 payload_mode = copy）。代价：026 迁移加列、global/register.rs 三处写入、版本链按 blob 指纹、分发要能拷回项目、global/tests.rs 补面——一整刀，不是顺手活。收益：归档里的 png / docx 能进全局、能分发，和表型走同一条链。 ② 分发后改名 现状 分发入口传的是 enqueue_distribute(root, name, None, false)，落名＝全局名。只有撞名之后才有改名：冲突框选「改名」→ ConflictChoice::Rename(name) → enqueue_distribute(root, global_name, Some(name), false)（panels/resources.rs:237）。所以是「撞了才能改」，不是「分发前能改」。 路径 A 维持撞名后再改：零改动，且与 §13.4「分发不弹前置框、点一下就走」一致。代价：两份同名的永远先撞一次，多一个往返（撞 → 框 → 改名 → 再分发）。 路径 B 分发前先取名：菜单加「分发并改名…」，开一个单输入框（复用冲突框里那个 rename 输入的形态）。代价：一个新对话框 + 一处菜单入口 + 测试；收益：省掉必然撞的那次往返。代价的另一面：分发从「一步」变「两步」，与 §13.4 的取向相反。
这两条与 25 块的链路不冲突；它们只决定边界上那几个进不了这条链的档，以及要不要给它们开口子。① 的「拒绝」已经进了代码，② 现在就是「撞了再改」。两处都等一句拍板。
