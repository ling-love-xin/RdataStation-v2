分发到本项目§13.6

全局行唯一能做的事：复制一份进当前项目。两处入口——全局行右键「分发到本项目…」（判据 !is_global || multi_count > 1 || read_only，不判本体状态）／08 块详情那颗 archive-detail-distribute（判据只有 read_only）。 跟升级一样没有确认框：点了即入队，撞名才开同名冲突（标题固定，与升级共用）。

索引← 上一块：升级到全局下一块：跨项目全流程 →
A两份形态与落点表 → 建项目表；脚本内容表 → 重建为文件
全局表 → 项目分析表（Analysis 档）
全局连接 COPY <名> TO '<tmp>.parquet' (FORMAT PARQUET) → 项目连接 CREATE TABLE <目标名> AS SELECT * FROM read_parquet('…') → project_table_stats 真量行列 → 登记 kind='analysis'。
为什么不用 ATTACH：Windows 单句柄限制下项目连接去 ATTACH 全局库文件会撞「文件被占用」（全局写连接由 GlobalDatabaseManager 持有），parquet 中转无锁冲突。
脚本内容表 → 项目文件（File 档）
读回 SELECT "content" FROM <名> LIMIT 1 整段，写进本项目 resources/<全局行记的 rel_path>（目录 create_dir_all、文件直接写）→ 登记 kind='file'、file_rel_path = rel。
重建路径固定用全局侧记的那条相对路径，不随改名变，也不重新猜目录。

形态判定只有一条：全局登记的 file_rel_path 非空 = 脚本档 → 重建文件；为空 = 表档 → 建表。用户看不到这个判定，也无法强制选另一种。
两侧落值都带 readonly = 1、promoted_from = 'global:<全局 id>'、payload_mode = 'copy'——项目侧「归档后只读」的规矩对分发下来的行同样成立。

B撞名的三查登记层 + 本体层 + 文件层，任一命中就询问
① 登记 ② 表本体 ③ 文件本体

报出去的名字是目标名（未改名 = 全局名）——三查任一命中都汇成同一个 Conflict { name }，框里只说「{持有方}已有同名资源「{目标名}」」，不说撞的是登记、表还是文件。 ② 查不区分 schema 与连接，只看 table_name——同库别的 schema 里有同名表也会判冲突。

C版本与来源旧稿写错的第 1、2 处：版本不接续全局链；来源看得见，但是内部 id
版本：从 v1 起，不是「接续全局 v2」
register_project_table / register_project_file 取的是项目侧 MAX(version) WHERE name AND scope='project' AND deleted_at IS NULL；首次分发项目里没有同名行 → 0 + 1 = v1。覆盖分支会先把旧行软删，deleted_at IS NULL 再查还是 0 → 仍然 v1。
所以回执里那个 v{n} 恒为 v1；全局版本号只写进快照的 global_version（见右卡）。
来源：详情里真会显示，且是内部 id
promoted_from = 'global:arp_<uuid>'，而详情「来源」区把它当「来源草稿」渲染（detail_view/rows.rs:52-54）→ 用户看到的是「来源草稿：global:arp_3f2a…」。表档还多一行「来源表：<目标名>」（source_table = 自己的名字，等于自己指向自己）；source_path 为 NULL。
详情「来源」区实际渲染的三行分发落下的表档
来源草稿global:arp_9c41d7e2… 来源表dwd_orders_view 指纹—（快照里的 content_hash）

「草稿出处」与「全局来源」挤在同一个字段上：升级侧恒 NULL（不记谁升过来的），分发侧塞 global:<id>，而显示口径只认识草稿路径。要让人看懂，得给分布来源单开一列或加一个「来自全局」的解析（本轮只记不改）。
快照里的 distributed_from / global_version 没有任何界面读——present/detail.rs 反序列化快照只取 kind / 文件大小 / 行数列数。所以「回到全局那条链接」不存在。

D撞名之后：覆盖 / 改名对话框本身就是 17 页 D 段那张，这里只记分发的两句文案
覆盖
文案原文：「覆盖将删除项目旧表 / 旧文件并软删旧登记，新内容接续项目版本链；旧本体不可恢复。」
选中后 enqueue_distribute(root, 全局名, target, true) + 状态栏「资产库：正在覆盖分发到本项目…」。
「接续项目版本链」这句不成立——覆盖后落到 v1（见 C 段）。
改名
输入框常驻、开窗已预填冲突名 → 打开瞬间必是 Unchanged（提示 warning、改名键灰、Enter 也提交不了）。改成别的新名且过闸（Ready）后 enqueue_distribute(root, 全局名, Some(新名), false) +「资产库：正在从全局分发…」。

对话框形态见 17 页 D 段：480px、标题固定「同名冲突」、无副标题、三颗 small 按钮（取消 / 覆盖（Danger 淡红底）/ 改名 Primary）、Enter = 改名、Esc = 取消。 分发与升级只换正文：持有方「当前项目」、动词「从全局分发」、覆盖后果换成上面那句。
另查：ConflictContext::Distribute { global_name, target } 决定冲突框正文里的名字——只有没改名时才等于全局名，改过一次名后正文说的就是那个新名。

E覆盖分支的两个坑只记不改：没有跨库事务；脚本档改名绕不过文件占位
覆盖 = 先删再看，三步跨三个地方
① DROP TABLE IF EXISTS <目标名>（无条件，不管目标是表还是文件）→ ② 若全局行有 rel_path 就删 resources/<rel> → ③ 软删项目登记（按目标名）→ 再走一遍 distribute。
DuckDB / 文件系统 / SQLite 各一次，没有事务；中途失败留下的是「表没了登记还在」或「登记没了表还在」——而重名三查对这两种脏状态只报同一个冲突名。
脚本档：改名字，不改文件路径
重建目标恒为 resources/<全局 rel>，改名只换登记名。于是项目里若已有这个文件（也许属于另一条不同名的资源），③ 查一直命中 → 冲突框一直报「已有同名资源「<新名>」」，换任何名字都撞同一道墙，且框里不会说「是文件占着」。

两条都是实现层面的账，不是规格没写：规格 §13.6 只要求「冲突时询问（覆盖 / 改名 / 取消）」，没说覆盖要做到原子、也没说脚本档撞文件时该怎么脱身。 真要修：覆盖三步收进一个「先算后改」的流程（或在失败时把已删的东西记下来回执里说清），脚本档要么把 rel 也当冲突目标、要么落文件时改名。
