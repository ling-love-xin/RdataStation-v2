升级到全局§13.3

本块现状：没有前置确认对话框。项目行右键「升级到全局…」点一下直接入队，状态栏只给一句「正在升级到全局…」； 只有撞名才开窗（17 块的覆盖 / 改名 / 取消）。目标名一律取显示名，代码里没有「先改名再升级」的入口。 变体 D 是本轮提的一个可选方案，规格里并没有这张框（§13.3 只在冲突时要求询问改名）——摆出来只为拍板，不当规格落差看。

旧稿第 2 步写错了两处：① 「白名单扩展名 → 表；其余（sql / py / md…）→ 内容表」——不是「其余」，是两张正向白名单，两表之外的二进制被单独拦下并给长回执（mod.rs:381-392 注释明写「不在两张表里的一律不允许升级」；这处是修 UTF-8 崩溃那批补的，见 开发计划）。② 分析表型那句回执在唯一的入口上不可达：菜单已用 !can_open 先置灰，详情面板也没有升级入口（全仓只有 menu.rs:111 一处调用）。

升级完成后项目行与全局行是两条独立登记：项目行不会因为升过级而变成只读，也不会互相跟随。

B四种结局，不是三种同一次点击，落到全局的东西不一样（第四种是「什么都不落」）
数据文件 → 真表
全局库 CREATE TABLE global.<名> AS SELECT * FROM read_xxx('…')；行数 / 列数由建完的全局表真量（table_stats），写进全局登记。
文本脚本 → 内容表
方案 A 定稿：单行表 (filename, content, content_hash)，正文整段进 content，不拆行。行数 1 / 列数 3 是写死的常量（promote.rs:112），不是量的。分发时再重建回文件（见 24 块）。
二进制 / 无扩展名 → 拒（有回执）
不在两张白名单里的文件：宿主在建库之前就拦下，回执里点名扩展名并给两条出路（另存 csv、或走分发 / 共享目录）。这类行在菜单上不置灰——能点，点了才知道不收。
分析表型存档 → 拒（菜单已灰）
本体在项目 analytics.duckdb 里，没有可读的相对路径。回执「随 M8 后续批次接入」存在，但用户触发不到——can_open 先把它挡在菜单外。见 26 块。

四个分支全在宿主那一侧判（扩展名白名单 + payload_rel_path 是否为空），面板上不给用户选形态——升级没有「按什么升」的开关。

全局侧只读：升级进来之后，任何项目都不能直接改它的内容，只能「复制到本项目」再改。
升级不改项目侧那份本体

为什么把它归到「方案」而不是「落差」：§13.3 只写了「表名默认取显示名，冲突时询问改名」，并没有要求升级前先弹一张确认框——那是本轮提的加法。实现选了「不确认、撞名才问」，与规格并不矛盾，只是能让用户在入队前先看到「形态 / 目标实例 / 版本」这三件会变的事。要不要加，得先定「升级前能不能改名」：不改名，就只能接受改名入口出现在冲突处置里。
框里那句「全局侧只读」有实现支撑：全局登记行 readonly = 1（见 D 段）。

两行的版本号各记各的：全局侧从 v1 起（或被覆盖时数字接续）。不要按名字把两行当成同一条记录的两种展示——它们没有联动，也没有「谁升过来的」这条线：register_global 落的是 promoted_from = NULL，只有 source_path（项目侧的绝对路径，换个项目/机器就没意义）。register.rs:229-248

全局行还有三处与项目行不同的落值：kind = 'analysis'（一律按分析表登记，不继承项目侧的 file / analysis 档）、readonly = 1（全局侧只读是登记行自己带的，不靠界面约定）、payload_mode = 'copy'。

E冲突与覆盖：三态同框、覆盖换 id
冲突检测是「先登记、再查表」双查
① 全局登记行同名（name + scope='global' + deleted_at IS NULL，取 MAX(version)）
② 全局 DuckDB 里同名表在不在（table_exists）
三种组合（表在登记不在 / 登记在表不在 / 都在）都返回同一个 Conflict { name }——注释里分了「脏状态」与正常冲突，但冲突框里看不出差别，用户看到的都是同一句「已有同名」。
「覆盖」= 删表 + 软删旧登记 + 新建一条
drop_global_table → UPDATE … SET deleted_at = ?（旧登记软删，不硬删）→ 再走一遍 promote
新版本号 = MAX(version) + 1，而这条查询不带 deleted_at IS NULL，所以软删行的旧版本号也算进去 → 数字接续得上
但版本链只在快照表里「数字接续」
每次升级都新生成 arg_<uuid>，版本快照挂在各自的 resource_id 下
→ 「版本历史」按 resource_id 查：新行只看得到自己那条 v2，看不到被软删的 v1（那是另一个 id）
→ 界面上「一条记录挂多版本」并不成立，只有版本号那串数字是连着的
回执：两条
入队那一刻「正在升级到全局…」；覆盖分支「正在覆盖升级到全局…」（panels/resources.rs:214）
完成后「已升级「X」v{n} 到全局实例（跨项目可分发）」——覆盖与首次升级共用这一句，回执里不说是覆盖还是新建

一句话的落差：设计稿 §13.2 说全局实例「表 + 版本信息进全局 DuckDB」，实现里版本信息进的是全局 SQLite 的登记表与快照表，DuckDB 只放表本体。这句话没写错但容易误读，已在设计稿里改准。
