本稿演示了什么 （点击上面这些地方；下面写的是每条对应哪条设计约束）

入口与生命周期

  • 活动栏第 4 个图标（插件）→ 左 Dock 面板；图标上的黄点是「有待授予的权限」
  • 列表三档：已安装 / 待更新 / 市场；条目是两行式（宿主 List 要求同行同高，故统一 44px）
  • 禁用一条 → 若它被当前项目引用，面板出现「被项目引用」警告行（plugin-dev-plan §4.8 对账；不对用户静默）
  • 卸载同样触发对账：插件没了，项目引用还在 → 占位与「移除引用」两个出路
  • 插件根目录是 <RDS_HOME>/plugins/（待补 paths::plugins_dir）； 注意仓里已有的 extensions_dir() 是 DuckDB 扩展的目录，两者不要混用

权限与信任（双轨，语义不通用）

  • 扩展（JS）轨：rds.metadata.read / rds.editor.completion / webview.export / net.fetch …
  • 驱动（native）轨：spawn.child_process / net.connect / fs.read_plugin_data / env.inherit
  • 两轨不互相折算：能读元数据不等于能开子进程（§4.6.1）
  • 签名：Ed25519 + 逐资源 SHA-256；未验证发布者带显式标签，不靠颜色区分
  • 点「授予」→ 状态从「待授权」变「已启用」，活动栏黄点消失

崩了会怎样

  • 状态栏右侧「扩展宿主」是可点的：点一下模拟宿主进程崩溃
  • 崩溃时：插件贡献的面板全部变灰 + 横幅提示 + 3 秒后自动重启；宿主自己的界面全程可用
  • 这正是 D1「独立扩展宿主进程」要买的东西（崩溃隔离），不是架构洁癖

本稿刻意没画的

  • 评分 / 下载量 / 排行榜 —— 市场形态未定（本轮不做在线市场，只做「目录 + 本地安装 + 签名校验」）
  • 「一键更新全部」—— 更新策略待定（§11 Q9 与更新策略都还没拍板）
  • 任何插件自己画的像素 —— 管理界面必须由宿主渲染，否则插件能伪装成宿主
