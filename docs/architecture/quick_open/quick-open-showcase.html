01

为什么它不是一个「搜索框」

V1 的标题栏输入框只是块装饰——这一版逐条换成真东西
旧样子现在
输入框只是外观，没有浮层、没有键盘通道 独立浮层实体（quick_open/palette.rs）：打开即聚焦、↑ ↓ 跨组漫游、↵ / Shift+↵ / Esc 三态确认
只能过滤一份写死的本地清单 三类来源：元数据（跨连接索引，异步）、文件（草稿箱）、连接 + 命令
没有模式概念 > 命令 / # 元数据全文 / 默认混排；前缀只认第一个字符，删掉即回默认
结果区手搓 div + on_mouse_down，无 hover / 选中态 组件库 List + ListDelegate：分组头（section header）、空态、hover / 选中 / 滚动全归组件
搜不到只给一个空列表 状态永远可见：组头「搜索中…」、门槛「再输入 1 个字符」、截断「还有 N 条」
执行动作内联在渲染闭包里 动作过端口（QuickOpenHost::execute），宿主只负责「做」；浮层不碰工作台内部
02

三档模式 · 一个入口

三档共用一个输入框，前缀只认第一个字符
前缀只认第一个字符（半角 > / #；全角 ＞ ＃ 当普通搜索词，避免输入法误触发）。
模式触发搜什么最小词长数据源
默认无前缀 元数据（表 / 视图 / 列）+ 文件（草稿箱）+ 连接 + 命令 元数据 2 字（本地源不受限） 每连接的元数据缓存库（后台异步）
命令> 仅命令（13 条，带稳定 id 与英文关键词，如 settings / database） 不发异步搜索 进程内目录（quick_open/commands.rs）
元数据全文# 全文档：schema / 表 / 列 / 视图 / 例程的注释与类型（视图定义 / 例程源码暂未纳入，见 §17 Q8） 3 字（trigram 的下限） 同库的 FTS5 表（metadata_fts）
门槛不是随手定的：名称档 2 字是为了不让每个连接都被扫一遍；全文档 3 字是因为 trigram 分词器下 不足一个 trigram 必然无命中（实测：中文注释搜「含渠道」命中、搜「渠道」无命中）。
03

三个高光

如果只记三件事

① 元数据搜索是核心，而它是索引直出的

名称档：先按类别（表 → 视图 → schema → 列）各扫一段 (connection_id, object_type, LOWER(name)) 索引， 取够一页就停——没有全量排序、没有近似窗口；排序键里连 LENGTH 都拿掉了，就为了让它能被索引直出 （8 万同前缀命中：158 ms → 1.5 ms）。全文档：FTS5 trigram + ORDER BY rank，中文注释可搜。

结果是：8 万命中 1.5 ms，而不是「等它排完」。

② 「在搜 / 没搜够 / 被截了」三件事，界面上都写着

组头右侧「搜索中…」、门槛提示「再输入 N 个字符」、组尾「还有 N 条（继续输入缩小范围）」—— 静默截断与静默空列表在这套界面里是不允许的（Group.hidden 承载被截条数，测试钉住）。

反例：「按了没反应」在这套界面里是不允许的。

③ 浮层是可测的实体，不是渲染闭包里的一坨

纯逻辑（前缀解析 / 评分 / 分组 / 截断）在 model.rs 是纯函数；浮层是独立 Entity； 宿主只实现一个端口 QuickOpenHost（执行动作 + 打开 / 关闭）。

于是窗口测试能真按键：Ctrl+P → 打字符 → ↑ ↓ → ↵ → 断言副作用。

四个剧本 · 它替你做什么

每一步都用现在就能敲的键，能照着做

剧本 A · 只记得表名的一半

→ 3 秒找到并打开属性
  1. 召唤：Ctrl+P——浮层在标题栏下方展开，焦点已在输入框（不用再点一下）
  2. 敲一半：敲 ord——命中按来源分组：元数据（表 · 视图 · 列）在最上，前缀命中排在子串命中之前
  3. 看一眼再决定：每行左侧是类型短标签（表 / 视图 / 列 / 模式 / 连接 / 命令 / 文件），右侧是所属 schema / 目录
  4. 进去：↵ 打开属性面板并定位该对象；Shift+↵ 不关面板，接着敲下一个

剧本 B · 只记得注释里写过「优惠」

→ # 档找字段
  1. 切档：输入 #优惠（前缀与词之间可有空格）
  2. 读片段：结果是两行式：第一行对象名 + 内容 标签，第二行是 snippet，命中片段带底色
  3. 定位：↵ 到属性面板；命中来自注释而不是名字，所以不做标题过滤（否则只在注释里命中的行会被误杀）

剧本 C · 忘了菜单在哪

→ > 档当命令行用
  1. 切档：输入 >设置、>隐藏、>新建查询，或直接敲英文关键词 settings / database
  2. 认准目标：每条命令显示快捷键；关键词参与匹配但不被高亮（不把你看不到的词标黄）
  3. 执行：↵ 立即执行；命令档不触发任何元数据搜索（不发异步、不打库）

剧本 D · 接着改上次的草稿

→ 默认档里就是文件
  1. 敲路径片段：文件行的匹配面是相对路径：敲 drafts/notes 或只敲目录名都能命中（高亮仍按文件名算）
  2. 打开：↵ 在中央编辑区打开该草稿（可写 / 只读由编辑器按路径判定）
  3. 清单太大：后台清单被截时，组头右侧写明原因；搜索仍在后台继续，不挡你敲字

07

名称档：两段式 + 分类索引序直出

中缀可搜 · 索引序直出 · 全程无 SQL 排序
名称档回答「按名字找对象」，所以必须支持中缀（敲 ord 要能找到 order_items）—— 这一点 FTS 的 trigram 做不到（< 3 字必然无命中），于是它走缓存库的 metadata_index 表。
段做什么怎么做到不慢
前缀段 >= needle AND <= needle‖U+10FFFF 范围比较（等价于「以 needle 开头」） 走 (connection_id, object_type, LOWER(object_name)) 索引；每类各扫一段，ORDER BY LOWER(name) LIMIT n 就是索引序，取够即停
回落段 前缀没装满一页时，用 LIKE '%needle%' 补名额 同一索引：LIKE 只当过滤谓词，排序仍由索引提供（旧写法是全表扫 + 全量排序）
合并 按「档位（完全相等 → 前缀 → 中缀）→ 类别（表 → 视图 → schema → 列）→ 名序」稳定排序 稳定排序保住类内索引序，所以不需要把 id / 长度拿进键；全程无 SQL 排序
10 万对象缓存库实测（debug，单连接，8 万表 + 2 万列；同轮并排跑旧写法）：
查询现在旧写法（单条中缀 + 全排序）
table_（8 万同前缀命中）1.5 ms158 ms
_0042（中缀，命中在列档）12 ms72 ms
table_000042（表档一条不中，须扫完整段才能确认）45 ms87 ms
无命中45 ms79 ms

第一步 · 前缀段走索引

178 ms

快，但排序还在——8 万同前缀命中仍要排完才给结果。

第二步 · 拿掉排序键里的 LENGTH

1.5 ms

排序退化成「相等 → 类别 → 名序」，恰好与索引序一致，于是窗口与排序一起消失，既精确又快。

剩下的成本

45 ms 稀疏词 / 无命中

稀疏词要扫完该档整段才能确认「没有」——再要降只能靠 trigram。

08

全文档：FTS5 trigram

trigram 让中文注释可搜，代价是 3 字门槛
维度取值
表metadata_fts（与 metadata_index 同在每连接的缓存库）
语料schema 名；表 = schema + 表名 + 表注释；列 = schema + 表名 + 列名 + 数据类型 + 列注释；视图 = schema + 视图名 + 视图注释；例程 = schema + 例程名 + 例程类型 + 例程注释
暂无语料view_definitions.view_definition 与 routines.routine_definition 已落在缓存里但没进 FTS（是否纳入见原型设计 §17 Q8）——今天能搜的是注释与类型，不是视图 / 例程源码；分组标题里的「注释 / 定义」是既有 UI 文案
分词trigram（迁移 011）——中文子串可搜，代价是查询 ≥ 3 字、索引体积约为文本 3 倍量级
清洗查询词先经 fts_match_query：拆词 → 逐词加引号 → 末词前缀；" * ( NEAR - 全按字面处理，不报错
返回类型 + schema + 对象名 + 父对象 + snippet（SQLite snippet() 生成的 <mark> 片段，直接转高亮）
写入时机与 rebuild_schema_index 同批（内省一个 schema 就刷新一次）；绝不在搜索路径写库，且 FTS 失败只告警、不拖垮导航赖以分页的索引
两个当场抓出来的底座缺陷（都已修，写在迁移 011 的注释里）：
① 旧表是 contentless（content=''）——MATCH 能命中，但 SELECT 回来的对象名全是 NULL （Invalid column type Null at index: 0），snippet 也无从生成，整条读路径其实不可用。
→ 迁移 011 重建为可读表：命中、读回、snippet 三件事同时成立。
② 旧分词器 unicode61 把连续中文当一个 token（「含渠道与优惠信息」是一个词），中文注释等于搜不了。
→ 换 trigram：中文子串可搜，实测搜「含渠道」命中。
09

键盘与选中

选中锚在业务键上——异步回填不抢光标
键行为
Ctrl+P打开 / 关闭浮层（与标题栏入口同一个）；打开即聚焦、清空上次输入、重置选中
↑ ↓跨组连续漫游（结果重算后按业务键回到原来那一行）
↵执行选中行：打开属性面板 / 建文档 / 切面板 / 选中连接 / 打开草稿
Shift+↵执行但保留面板（连续操作不用重开）
Esc一次即关（不做两段式清空）；未回的批次照常丢弃
鼠标悬停高亮、点击执行；点击遮罩关闭
选中不是按行号锚的，而是按业务键（qo-row-{key}）：异步回填时新结果插进来也不会把光标顶走。 这条与「排序稳定」「id 兜底」是一组——三者合起来才让结果不跳。
10

异步与状态

150 ms 防抖 · 过期丢弃 · 不建缓存 · 不抢选中
规则说明
单输入源浮层里只有一个输入框；标题栏入口只负责「打开」
防抖元数据是读盘 + 跨连接：150 ms 防抖，且只在查询词变化时才发
过期批次丢弃回填结果自带 query，与当前输入不一致直接丢（SearchResult 语义）
不建缓存查询不为未内省过的连接创建元数据文件（cache_file_exists 门）——搜索不该顺手建文件
双消费方分槽nav_jobs 按 SearchConsumer::{Navigator, QuickOpen} 分槽：导航与浮层同时搜不互抢结果
不抢选中镜像宿主选中时用 begin_host_sync / end_host_sync 守卫，避免「更新正在被更新的实体」
重绘状态变化后通知宿主重渲染（Shared::notify_host）

workbench → database → engine；浮层不碰 SQLite

纪律含义
依赖只向下workbench → database → engine；浮层不直接碰 SQLite，也不拿宿主内部实体
渲染零 I/O渲染期只读内存快照；搜索 / 文件清单都在后台，回填走泵
纯函数优先前缀解析、门槛、评分、分组、截断都是无窗口纯函数（model.rs 13 项单测钉住）
端口只有一个QuickOpenHost::execute(action, keep_open, window, cx)——宿主做「怎么做」，浮层只说「做什么」
组件不许手搓结果区是组件库 List + ListDelegate；尺寸取自 workbench_shell/src/ui.rs 常量，取色走主题 token

质量与证据

每个功能都指得出「哪些测试在守它」
套件数量覆盖
rds-workbench --lib110 项 含 Quick Open 专项：model.rs 纯逻辑 13 项（前缀解析 / 门槛 / 命中区间 / 评分分档 / 分组过滤 / 命令键唯一与关键词可命中 / 截断计数 / 文件行匹配面…）
rds-workbench --test ui_contract7 项 新模块必须登记进尺寸 + 颜色两份清单（漏登 = 契约对该文件静默失效）；视图层零裸尺寸、零裸色值
Quick Open 窗口测试5 项 真按键走生产入口：打开即聚焦 / ↑ ↓ + ↵ 经端口执行并关面板 / Esc 关闭 / 单字符门槛 / 文件源
rds-engine --lib446 项 含搜索专项：两段式 vs 单条查询逐条等价、窗口取消后的「精确 + 类别优先」、两段 EXPLAIN QUERY PLAN 断言（走索引且无 TEMP B-TREE）、FTS 写入幂等与读侧身份 + snippet + 中文门槛
rds-database --lib55 项 含 FTS 命中映射（空串 → None、catalog 缺位）与分槽通道
规模基线（#[ignore]，手动跑 --ignored --nocapture）：10 万对象（8 万表 + 2 万列）缓存库， 同轮打印「现写法 / 旧写法」并拆出两段耗时——第 7 节的数字就来自它，改搜索实现时重跑即可复核。
实证缺陷（开发期当场抓出来，都已修）：
① FTS 旧表 contentless → 读回全 NULL、snippet 无从生成。
→ 迁移 011 重建为可读表。
② 中文注释因 unicode61 分词整句一个 token 搜不到。
→ 换 trigram，「含渠道」这类中文子串可搜。
③ 名称档排序键含 LENGTH → 索引只能加速「找」不能加速「排」，8 万命中要 178 ms。
→ 拿掉 LENGTH，排序与索引序一致：158 ms → 1.5 ms。

边界 · 这些事它不做

把话说在前面，比事后解释便宜
不做为什么
不检索数据行那是查询与结果区的事；这里只找对象（表 / 列 / 视图 / 文件 / 命令 / 连接）
不做拼音 / 模糊纠错元数据名多是英文标识符；模糊匹配会把「搜不到」的锅变成「搜出奇怪的」
不为搜索建元数据缓存未内省过的连接直接跳过——搜索是只读动作，不该产生副作用
不自动连接数据库↵ 命中连接只选中它（切到导航），连不连由你决定
不在搜索路径写索引FTS / 索引的刷新只在内省同批发生；搜索期间库是只读的
不做「静默截断 / 静默空列表」截了多少、在不在搜、门槛差几字，都写在界面上
还没做的（原型设计 §17 待拍板 + §18 优化清单）：@ 当前连接限定 · 行内动作（复制限定名 / 生成 SELECT）· 空输入态的「最近 + 常用」· 结果短时缓存 · 并发打开缓存文件上限 · 结构化日志（query_len / hits / dur_ms / conns_skipped）· 中缀稀疏词的 trigram 兜底。
关于「升格为 crate」：暂不拆。触发条件是——出现第二个宿主（独立窗口 / 插件面板）、 插件系统需要注册命令与搜索源（palette 成为对外契约）、或「最近使用」需要独立持久化。 今天它是 workbench 里的一个模块，边界（纯逻辑 / 浮层 / 端口 / 委托）已经是 crate 的形状。
