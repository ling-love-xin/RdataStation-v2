# 洞察模块（M8）· DuckDB 扩展评估与可采取之处

> 状态：**讨论稿 / 记录**（2026-09-18）——本文不是契约；契约部分是架构 **D61**（实现手段边界：三层实现 + 扩展准入）。
> 关联：`insight-architecture.md`（D61 / §11 已知问题）、`insight-dev-plan.md` §10（未接与预留项收口清单）、`insight-user-guide.md`（FAQ 里的 Excel 扩展那条是同一问题的先例）。
> 读法：**§6「可采取之处」是本文的行动项**，其余是依据。凡带"待核实"的都是我（AI 调研）未逐条跑过的判断，落地前要有探针。

## 1. 现状约束（决定成本的三件事）

| 约束 | 事实 | 出处 | 后果 |
| --- | --- | --- | --- |
| duckdb 是**外部编译库** | 1.5.5，取到 `third_party/duckdb/<版本>/`，路径走 `.cargo/config.toml` 的 `[env]`；静态库并发链接会 OOM（全仓 `-j 2` 的由来） | 根 `Cargo.toml` 注释 + `tools/fetch-duckdb.sh` | 扩展必须与 **1.5.5 + 平台**精确匹配；每次升级 duckdb 都要复核每个扩展 |
| 洞察跑在**单例内存库**上 | mock / 编辑器（本地加速）/ 联邦 / 结果集 / 洞察共用同一 DuckDB 实例 | D13 / D51 | `LOAD` 是**进程级**的：新扩展的函数面对**所有**功能可见，安全门（D52）要同步处置 |
| 扩展机制**已有** | `ExtensionManager`（discover / install / load / unload + 名字白名单 + 状态缓存）；`fts` 模块；excel 扩展已用于 `read_excel_auto` | `engine/src/duckdb/extensions.rs`、`docs/architecture/insight/insight-user-guide.md` FAQ | 边际成本已降低；但每个新扩展仍是一格**分发矩阵**（离线 / 内网要预置 + 指定 extension_dir） |

补充事实：社区扩展默认**带签名**（社区仓库 CI 签名，清单只列最新稳定版，即 1.5.5），因此不需要打开 `allow_unsigned_extensions`——这一点比自己编译扩展安全。

## 2. 边界（写进 D61 的那几条）

### 2.1 三层实现

```
编排层（我们，必有）      类型分派 / NULL 语义 / 采样口径 / 质量模型 / 治理 / 呈现
内置计算层（默认）        DuckDB 内置函数与语句（SUMMARIZE / quantile / corr / histogram …）
扩展层（可选）            白名单 + 版本锚定 + 签名 + 可降级；只在前两层表达不出时才进
```

### 2.2 最锋利的判据

> **扩展可以换实现，不能换语义；扩展的产物不许成为长期格式（除非我们自己定义版本化的序列化契约）。**

两条推论：

- **同语义要求**：依赖扩展的结论，在"只靠编排层 + 内置"时必须能给出**同一种结论**（可以更慢更粗，但不能是另一种东西）。做不到 → 那是**新能力**，要走产品决策，不是技术选型。
- **产物判据**：快照要活 30 天（D56）且跨版本存活，而扩展与 duckdb 版本强绑定。所以数值结论（值 + 方法标识）可以进快照；扩展私有二进制（如 DataSketches 的 sketch）**不许**——除非我们先有自持的序列化契约 + 版本号 + 读回兼容策略。这是 datasketches 那条路真正的门槛。

### 2.3 准入四件套（缺一不可）

1. **白名单**：名字进受信任列表（`ExtensionManager::validate_extension_name` 已有，需加"受信任"语义）
2. **版本锚定**：扩展版本与 duckdb 版本**成对**登记；升级清单里带上它
3. **静态门登记**（D52）：它带来的新函数族默认拒绝、显式放行；文件 / 网络类函数一律不放行
4. **降级 + 退出**：不可用时退回内置实现并回答"缺什么"（照 Excel 那条先例）；引入时即写明"怎么移除"

### 2.4 能力准入顺序

新增分析能力：① 先试**一条规则**（`.rule.toml`，自带治理、零分发成本）→ ② 再试**内置 SQL** → ③ 都表达不出，才进"扩展候选"。

> 这条的意义：**规则引擎是本模块的第一个扩展面**。绝大多数"想要一个新统计量"的诉求应该在 ① 就消化掉。

## 3. 候选扩展逐个评估

| 扩展 | 官方定位（v1.5.5 社区清单原文摘要） | 与我们重叠 | 判断 |
| --- | --- | --- | --- |
| `dq` | 数据质量断言框架：SQL-native `expect_*` 规则、profiling、**持久化质量报告** | **完全重叠**：规则引擎（三层作用域）+ 质量评分 + 快照 | ❌ 不替换（我们治理更严：D52 静态门 + D53 信任门 + 索引 + 版本链）；✅ **抄接口**（见 §6.7） |
| `dqtest` | **不在 v1.5.5 社区清单**（疑为 dq 配套测试仓库 / 旧扩展，待核实） | 测试工具，非分析能力 | ❌ 不引 |
| `stats_duck` | 描述统计 + **假设检验** + R 风格分布函数（d/p/q/r）+ **OLS 回归（HC / 聚类稳健标准误）** + Vega-Lite 图表 + SAS / SPSS / Stata 读写 | 描述统计重叠；检验 / 回归 / 分布是新增 | 🟡 要"推断性结论"时的第一候选；先看 §6 里"规则能不能表达"再定 |
| `stochastic` | 统计分布函数、概率计算、随机采样 | 与 **M7（mock 生成）** 更近 | 🟡 转 M7 评估；M8 侧只对"分布检验"有意义 |
| `datasketches` | 近似 distinct / 分位数估计，**sketch 可序列化** | 内置 `approx_count_distinct` / `quantile_*` 已覆盖单机场景 | 🟡 唯一独特价值：**sketch 可合并 + theta 集合重叠**；受 §2.2 产物判据约束，当前场景（500 行样本）用不上 |

## 4. 顺带发现的其他候选（用户未提，但与本模块相关）

| 扩展 | 官方定位（摘要） | 与我们的关系 |
| --- | --- | --- |
| `finetype` | 语义类型分类：从原始字符串识别 251 种类型（email / URL / 日期 / UUID / 货币…） | **与类型族判定 + 「类型不一致」+ 质量评分直接相关**：可把质量从"声明类型一致"升级到"语义类型识别"（VARCHAR 里混邮箱与手机号今天看不出来）。§6.6 |
| `duck_diff` | 按主键 diff 两个关系：per-key 状态（identical / different / left_only / right_only）+ 逐列左右值 + JSON 摘要 | 「版本对比」的输出形状范本（我们现只比列画像数字）。§6.5 |
| `gatekeeper` | **执行前**授权检查：不执行查询，对解析出的表 / 视图 / 函数做可锁策略检查 | **与 D52 静态门同一问题域**，且"不执行查询"的定位与我们一致。§6.4 |
| `anofox_tabular` / `anofox_statistics` / `anofox_forecast` | 表格数据质量与准备工具 / 回归与推断 / 时序预测（ARIMA / ETS / GARCH…） | 若产品要"分析结论"（不是画像），这是 stats_duck 之外的备选；时序能力目前完全空白 |
| `textplot` / `miniplot` / `ggsql` / `anofox_visualization` | SQL 内出图（ASCII / Vega-Lite / ggplot-rs） | 印证 D21/D22 的"只出 `RenderHint`，渲染归 M5/M6"；也提示 RenderHint 将来可映射到这些输出契约 |
| `system_stats` / `table_inspector` / `observefs` | 系统统计 / 存储内部检查 / IO 可观测 | D51（内存闸 + 登记概览）的同族；可照"可查询视图"把洞察的临时表与内存状态暴露给排障。§6.9 |
| `pac` | 查询私有化（PAC 隐私框架） | 未来的隐私边界参考（若做敏感数据画像） |
| `anofox_scenario` | 分支式分析库（branch / diff / merge what-if） | 与我们"追加式版本链"（D18 / D57）是不同范式，供对照 |

## 5. 可参考的扩展设计（设计本身，不是功能）

### 5.1 DuckDB 生态内

- **`gatekeeper`**：策略对象 + "检查解析结果而非关键字"——D52 的升级方向。
- **`dq`**：断言**词表**设计（`expect_*` 原子化）+ profiling 输出 + persisted reports 的形状。
- **`datasketches`**：把"结论"建模成**可合并的状态对象**（而非数字）；这是"分布漂移"类能力的原型，但受产物判据约束。
- **`duck_diff`**：diff 的**输出形状**（per-key 状态 + 逐列左右值 + JSON 摘要）。
- **`finetype`**：**语义类型分类学**（层级命名 + 置信度）作为质量维度。
- **`system_stats` / `table_inspector`**：把内部状态做成**可查询视图**。

### 5.2 生态外（数据质量 / 画像领域的公认范式）

- **Great Expectations**：**"期望"三层分离**——语义契约（`expect_*` 声明）→ 度量（怎么算）→ **结果形状**（success / observed_value / unexpected_count / partial sample / exception_info）；`ExpectationSuite` 组合；Data Docs 报告。**与本模块最值得对照的一条**（见 §6.2）。
- **Deequ / pydeequ**：**约束（Constraints）与度量（Analyzers）分离** + **Metrics Repository**（度量可存可查、按时间对比）。与本模块结构最像；它正是 K6 的正解形状（见 §6.3）。
- **dbt tests**：**少量内建 + 参数化 + 项目自定义**三段式（与我们的三层作用域同构）；`store_failures`（失败行落表）。
- **Soda（SodaCL）**：人类可读的断言 DSL；checks / metrics 分层；"一行一条"的可读性。
- **pandera / frictionless**：schema-first 校验与"数据描述文件"（Table Schema / Data Package：字段类型 / 约束 / 缺失语义）——画像反向产出规范的参考（§6.10）。
- **ydata-profiling**：报告分区（overview / variables / interactions / missing / sample）与 alerts 分级——我们四区画像的对照物（缺"列间关系"一区）。
- **OpenLineage / OpenMetadata / DataHub**：把质量结果做成**可查询的一等资产**（时间序列 + 血缘）——K6 的长期价值方向。
- **Postgres `CREATE EXTENSION` / SQLite virtual table / DuckDB core vs community 分发**：扩展的**分发与信任模型**（core 随版本走；community 独立 + 签名 + 只列最新版）——若将来要做"规则可分享/规则包"，参考 dbt package 的版本化依赖与 community 的分发纪律。

### 5.3 内部先例（别忽略）

本仓已有的三条通道本身就是"扩展设计"，新能力优先复用而不是另起一套：`ThemeRegistry::watch_dir`（规则热加载照它）、`ExtensionManager`（扩展安装/加载/白名单）、`InsightStorage`（快照双写 + 回滚）。

## 6. 可采取之处（**行动项**；不必引入任何扩展）

> 每条给：参考什么 → 落在哪 → 是否改代码 → 优先级。P0 = 成本极低 / 直接补短板；P1 = 有价值但要设计；P2 = 排期靠后。

| # | 可采取之处 | 参考 | 落点 | 改代码 | 优先级 |
| --- | --- | --- | --- | --- | --- |
| 6.1 | **用内置 `SUMMARIZE` 做画像交叉校验**：把它的输出（类型 / approx_unique / avg / std / null% / min / max）与我们"基础统计"逐列对照，作为诊断路径或测试断言 | DuckDB 内置 | `insight_engine` 的诊断/测试（不改产品行为） | 否（测试级） | **P0** |
| 6.2 | **规则产物补"观察值 + 异常样例"**：① `observed_value`（即使通过也记实测值）② 失败样例（限量、脱敏）——把"72 分"变成"72 分，因为空值率 41%（样例 5 行）" | Great Expectations 的结果形状 | `rule_executor` / `QualityReport` / 面板「数据质量」区 / 快照 | 是 | **P0** |
| 6.3 | **表级 / Schema 指标落库**（K6 的正解）：把表级质量与 Schema 健康分按时间存下来（两张空表已在），支持"上周 vs 现在" | Deequ 的 Metrics Repository | `save_table_quality` / `save_schema_insight` + 面板保存入口与历史视图 | 是（中） | **P0**（需产品点头：表级快照的比对语义与列级不同——行数、列清单都在变） |
| 6.4 | **静态门升级为解析级策略检查**：从"关键字黑名单"改为"对解析出的表 / 函数 / 视图做策略检查"（解析能力 `engine/src/sql` 已有） | gatekeeper | `rule_registry` 的静态门（D52 加强） | 是（中） | P1 |
| 6.5 | **表级 diff 的输出形状**：per-key 状态 + 逐列左右值 + JSON 摘要，用于"表级快照对比"的视图模型 | duck_diff | `model.rs` 的对比视图模型（与 6.3 配套） | 是 | P1（等 6.3） |
| 6.6 | **语义类型识别作为新质量档**：「类型不一致」之外加「**语义不一致**」（同一 VARCHAR 列里混邮箱 / 手机号 / 纯数字文本） | finetype 的分类学 | 类型族判定之外的新识别器 + 质量维度 | 是（中） | P1（需产品：这是新能力） |
| 6.7 | **内置规则的参数化模板**：让内置规则可"带参复用"（阈值 / 值集 / 正则作参数），而不是复制整份 TOML 再改一行 | dq 的 `expect_*` 词表 + dbt generic tests | 规则 schema + 规则管理对话框「新建」入口 | 是 | P1 |
| 6.8 | **规则文件的可读性**：给业务读者看时"一行一条"更好读（现为结构化 TOML） | SodaCL | 规则模板 + 文档（不改 schema） | 否 | P2 |
| 6.9 | **可查询的内部状态**：洞察临时表 / 内存闸 / 运行中任务做成可查询视图（排障） | `system_stats` / `table_inspector` | D51 的延伸（诊断入口） | 是 | P2 |
| 6.10 | **数据描述文件导出**：把画像结论反向产出"列规范"（类型 / 值域 / 唯一性 / 缺失语义），可导出、可作下次校验基线 | frictionless Table Schema | `schema_view.rs` 的导出家族 + 新格式 | 是 | P1（与 6.2 / 6.3 天然配套） |

**不做**：不用扩展替换规则引擎与质量评分（`dq`）；不引 `dqtest`；`stochastic` 转 M7。

## 7. 若将来要引入扩展：探针口径（准入前置）

1. **先验证加载**：外部编译库能否加载官方 / 社区扩展（`duckdb_platform()` 与 `duckdb_version()` 必须匹配）——这一步不过，后面全是空谈。
2. **用真实数据对比**：数值 / 文本 / 日期 / 全 NULL 四类列，跑扩展实现 vs 内置实现，量三件事——精度（对精确值的偏差）、耗时、**内存峰值**（对 2GB 闸 D51 的影响）。
3. **离线路径**：预置扩展文件 + `extension_dir`，验证企业/内网场景（无网络）。
4. **失败模式**：版本不符 / 未签名 / 文件缺失时，报错是否可读、能否降级。
5. **分发清单**：扩展文件大小、平台矩阵（win / mac / linux × x64 / arm64）、与 duckdb 版本的绑定关系——进升级清单。

## 8. 一句话结论

扩展能替代的是**统计函数**这一层（最不该自研、也不必替换）；替代不了的是类型分派与 NULL 语义、质量模型、规则治理、采样口径、快照与对比、呈现——那才是本模块的差异化。因此：**不为"功能多"引扩展，只为"内置与规则都表达不出"引**；而 §6 的那些"可采取之处"不需要任何扩展就能拿到大半收益。
