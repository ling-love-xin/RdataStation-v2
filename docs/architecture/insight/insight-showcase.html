01

为什么它不是一个「统计面板」

七处「看着有、实际是假」的地方，逐条换成了真东西
旧样子（V1）现在
底部四个 Tab 容器，多个面板压根没挂载——点进去是空的 右 Dock 五 Tab + 一个目标模型（列 / 表 / 多列 / 结构 / 历史）；每个 Tab 都取得到数，取不到就说清为什么
质量评分卡：组件在、数据恒空 四维评分真算，列级与表级共用同一套阈值；全空列不产分——没有依据就不给分
历史能看、没有保存入口（v1 的保存函数前端不可达） 保存入口就在历史 Tab 顶部（无项目时置灰并写明原因）；双写成对，失败回滚已写入的那一半
多列分析从未跑通 重新设计：列序即参数序 + 类型族过滤 + 结果与门控提示同屏，失败不冲掉表单
存储用量是前端估算 后端真实统计；拿不到就整行不显示（编一个 0 会让人以为历史被清了）
导出 / 规则热加载 / 适用规则标签都没有入口 结构报告导出 JSON / Markdown；规则走目录监听热加载，⚙ 对话框里可启停、可新建
filterByValue（按值筛选）语义错误 删除——洞察只做「结论」；交互式筛选属编辑器（M5），不在这里重造
02

三个高光

如果只记三件事
HIGHLIGHT 1

每个数字都说得出出处

四维评分算总分、总分定等级，同一套阈值列级与表级共用；类型族来自真实元数据（驱动接口，不靠名字猜）。 该没有的数字就真的没有：全空列不给分、分布画不出说明原因、历史读不到就不显示用量。

采样口径常驻写明类型族不猜与 DuckDB SUMMARIZE 交叉校验（测试级）
HIGHLIGHT 2

边界诚实，说不做的就真不做

能洞察的只有能出现在导航树上的对象（真驱动 + 活连接）与草稿箱 / 分析存档两块文件； 只靠 ATTACH 或三方扩展到达的远程库不在承诺范围内。每一句「做不到」都带着原因。

无项目：规则管理与快照置灰并写明历史 Tab 无项目时说“先打开项目”没实现就不摆按钮
HIGHLIGHT 3

规则即文件，扩展不用改 Rust

16 条内置规则 + 三层作用域（内置 → 全局 → 项目）+ 目录监听热加载：写一个 *.rule.toml 就多一种洞察。两道安全门：规则 SQL 过解析期静态门，项目规则过信任门。

解析期校验（value_type / 门控字段）一条被拒就是整条不加载正文以文件为唯一真相源

05

列画像 · 四区与评分卡

分数是这一列的头号结论，不该滚走

▤四个折叠区

  • 基础统计：总行数 / 非空 / 去重 / 极值等——行数与质量分基于全量统计
  • 数据分布：数值直方图 / 布尔占比；样本不足或类型未识别时说明原因，不造假分布
  • 数据质量：提示列表（Info / Warning）；没有问题就说「未发现需要提示的质量问题」
  • 样本数据：前 5 行，NULL 显式呈现；超长值按 200 字符截断
面板宽 17.5rem 起步（右 Dock）· 折叠态属用户偏好：⟳ 重算与切 Tab 都不会清空

★评分卡（钉在滚动区之外）

  • 总分 + 五档等级（优秀 / 良好 / 一般 / 较差 / 差）
  • 四维细条：完整性 · 唯一性 · 类型一致 · 分布均匀——每根条子按该维自己的等级取色，短板一眼可见
  • 全空列不产分；维度分数与总分同源，不会互相矛盾
列级与表级共用同一套阈值与文案（quality_scorer.rs）

结构报告 · 四区与下钻

空区照常渲染：空 = 检查过、没问题

◫报告长什么样

  • 健康条：分数 + 等级 + 「N 表 · M 列 · 需关注 K 项」+ 摘要
  • 四区：外键候选 · 类型不一致 · 孤立表 · 冗余列
  • 下钻：表名热点最多 4 个（长清单会把面板变成一条链接列表）
  • 导出 ▾：JSON / Markdown，导出的是你屏幕上这份结论
内容在面板侧算好（与界面同源的视图模型），宿主只选路径与写文件

⌖为什么 SQLite 也能用

结构取数只走 驱动元数据接口（列表 / 列 / 主键 / 外键），没有方言分支、没有手写 SQL—— 方言差异留在驱动层。真机四库因此全绿，也顺手把「按小写列名找 MySQL 元数据」这类坑堵在驱动侧。

真机数字见第 12 节的「质量与证据」

规则 · 加一个 TOML 就多一种洞察

16 条内置：列 9 · 多列 4 · 表 3
作用域 1
内置
编译期内嵌的 16 条；可被禁用（禁用记在索引里，不改文件）
insight-rules/
作用域 2
全局
用户级，跨项目生效
{系统数据目录}/insight-rules/
作用域 3
项目
随仓库走、可 diff、可评审；未信任前不装配不执行
{项目}/.RSmeta/insight-rules/
生效方式
目录监听
目录一改即热加载（不设「重新加载」按钮作唯一入口）
service/watcher.rs
# {项目}/.RSmeta/insight-rules/column/null-check.rule.toml
[meta]
id = "null-check"
name = "空值率检查"
category = "column"
applies_to = ["Any"]            # 任意类型都能跑

[query]
template = """
SELECT COUNT(*) AS total,
       COUNT("{col}") AS non_null,
       ROUND((COUNT(*) - COUNT("{col}")) * 1.0 / NULLIF(COUNT(*), 0), 4) AS null_rate
FROM "{table}"
"""
parameters = ["table", "col"]

[[output]]                      # SQL 列 → 界面字段 + 值类型（解析期校验）
sql_name = "null_rate"
json_name = "null_rate"
value_type = "f64?"             # 空表时 NULL：没有空值率可言

[[quality]]                     # 质量门控：读的就是上面的输出字段
field = "null_rate"
max = 0.1
severity = "warning"
message = "空值率超过 10%"

⚑校验早失败

  • value_type 在白名单里（报错说清哪个输出字段用了什么值 + 可用取值）
  • 门控字段必须真实存在（报错列出该规则已有的输出字段）
  • 一条规则被拒就是整条不加载，不会「部分生效」

⛨门 1 · 解析期静态门

只放行单条 SELECT / WITH；拒分号多语句、DDL 与 ATTACH / COPY 等、read_* 等表函数（校验前先剥字符串与注释）。

定位是防呆，不是安全边界——DuckDB 没有官方解析沙箱

⛨门 2 · 项目规则信任门

项目层规则在用户做出决定前不装配、不执行；决定记在全局库（项目碰不到的地方），首次遇到时弹一次确认框，之后可在横幅改主意。

无记录 / 查库失败一律按未决定（fail closed）；已知取舍：信任绑路径而非内容

架构 · 依赖只向下

状态只有一个写入者；渲染路径零 I/O
入口 · 装配
workbench：右 Dock 面板装配、订阅面板事件、把「下钻 / 导出 / 取样」翻译成宿主动作。components/{nav_host,resource_host,scratchpad_host}.rs · services/editor_insight.rs
视图 · 面板
insight_view.rs 状态宿主（目标 / 五态 / 各 Tab 载荷 / 选择与折叠）+ view/ 按 Tab 分的渲染片段（header · column · table · multi · schema · history）。点击只改状态并发事件。
接缝 · 服务
jobs.rs 把事件变成后台任务并回填；service/ 是同步门面（列 / 表 / 多列 / 结构 / 快照 / 清理）。面板不自己取数——这是「谁在写状态」只有一处的原因。
分析 · 规则
insight_engine / quality_scorer / schema_analyzer 出结论；rule_* 负责规则解析、校验（解析期静态门）、执行与注册表（三层作用域）。
存储
store/ 快照双写：正文进项目 DuckDB、版本链与元数据进项目 SQLite；写失败成对回滚，清理成对删。
引擎 · 数据
engine：DuckDB 连接与分析临时表（duckdb/analysis.rs，内存闸 2 GB / 溢写 10 GB）、驱动元数据接口（结构洞察不写方言 SQL）。
依赖方向：insight → engine → shared ·workbench → insight ·面板不直接碰驱动连接
关注点落点
状态宿主（目标 / 五态 / 各 Tab 载荷）crates/insight/src/insight_view.rs
渲染片段（按 Tab 分七个文件）crates/insight/src/view/
规则对话框 · 结构报告视图crates/insight/src/{rule_view,schema_view}.rs
快照存储（双写成对回滚）crates/insight/src/store/
分析临时表生命周期 · 内存闸crates/engine/src/duckdb/{analysis,temp_table}.rs

◈真机（需要环境变量，缺了就跳过）

  • insight_schema_real：结构洞察四库全绿——MySQL 47 表 / 318 列 · PostgreSQL 25 / 144 · SQLite 27 / 125 · DuckDB 10 / 27
  • insight_source_real：源取样四库 + 扩展源（Oracle 经扫描器）的机制回归
  • insight_editor_entry：编辑器结果集入口端到端（含真机腿）
扩展源那条是机制回归，不是边界判据——边界口径见第 14 节

⌖真机抓出来的真缺陷（都已修 / 结案）

  • 洞察取数照 JSON 契约读引擎结果 → 恒得空行（改为进程内直读列与行）
  • 门面自建一次性 runtime × 宿主 sqlx 池 → PostgreSQL 下一条语句卡 30 s（改进程级单例 runtime 后 30.2 s → 16 ms）
  • MySQL information_schema 的元数据列名全大写，按小写找列一个都读不到
  • 类型族判定没剥 UNSIGNED → 数值列被判成未知
每条都写进「已知问题」清单，带着现象与修法

边界 · 这些事它不做

把话说在前面，比事后解释便宜

✕明确不做（交给对应模块）

  • 不做 SQL 执行与结果集（M5 编辑器）：不画网格、不做交互式筛选
  • 不做对象树与元数据内省（M4）：导航树上有什么，取决于导航模块
  • 不做连接与运行态（M3）：连不上如实报原因，不自己重连或换库
  • 不物化结果集：编辑器入口重跑取样，因此「结果集临时表」的定向回收口维持空转
  • 不做表级 / Schema 快照与快照对比（二期）：语义属资产管理，界面与资产模型归 M6

◷如实声明与还没做的（都记在册）

  • 解析期静态门是防呆不是沙箱；信任门绑定项目路径而非内容（git pull 带进来的新规则不会重新确认）
  • 只能靠 ATTACH 或三方扩展到达的远程库不在承诺范围内
  • 静态门升级为解析级策略检查 · 源目标下「多列」Tab 预取样
  • 表级 / Schema 快照 · 分析表型存档入口（等 M6 Phase 4 本体层）
